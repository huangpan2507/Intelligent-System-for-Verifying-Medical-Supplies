## 1. 目标和边界

监管端只配置三个业务项：医院范围字符串、医保结算时间范围、规则选择字符串。平台负责解析机构、解析规则、确定明细、执行和保存结果。

- 时间范围严格限定医保结算记录。示例“2024年6月—2025年8月”规范化为 Asia/Shanghai 的 `[2024-06-01 00:00:00, 2025-09-01 00:00:00)`。不得为补齐就诊或计数范围追加范围外结算。
- 规则字符串选择已登记方案，具体筛选条件、检查窗口、部位词表、比较规则和字典由平台维护。
- 来源身份和幂等键是接口元数据，任务编号由平台返回，均不增加监管业务人员的填写项。
- 保留当前00—08业务画布和Verification可拖拽组件。范围发现和批处理落在现有业务服务中，图仍控制业务阶段顺序。
- 首期先完成单执行实例、分页处理、固定版本和完整模拟联调。新需求不自动包含持续增量、任意节点恢复、多机扩容或模型训练。

## 3. 职责与业务对象

建议保持现有服务边界：Langflow负责编辑、发布入口及图执行；核验业务API、Worker和业务库负责规则目录、受理、业务进度、证据及结果。不增加新的通用规则引擎或一套微服务。

| 对象 | 含义 | 变更方式 |
|---|---|---|
| RuleDefinition（规则目录项） | 稳定rule_code、名称、别名、所属范围、草稿flow_id | 管理名称和草稿关联；编码稳定 |
| Flow草稿 | 用户从Verification拖节点并配置的画布 | 随时编辑保存，调试使用 |
| RuleRelease（发布包） | 一次核验方案的完整可执行定义 | 发布后内容只读，修改产生新版本 |
| ActiveRelease（启用关系） | 某方案在某环境的新任务默认采用哪个发布包 | 原子切换并保留操作记录 |
| ExecutionBinding（运行环境绑定） | 运行地址、连接引用、环境模式、可用执行包 | 保存修订号，运行时固定引用 |
| Task | 外部一次业务委托及规范化医院/时间/方案 | 同号重试复用；不能覆盖原始范围 |
| Run | 一次实际核验，绑定release_id、binding_id、job_id | 重跑创建新Run；旧Run保留 |
| SettlementSnapshot及明细清单 | 本次实际取得的结算记录及其范围依据 | 查询期间构建，完整后封存 |
| VerificationUnit及阶段工件 | 可比较的业务分组、各阶段处理状态及证据 | 按运行隔离、逐组持久化 |
| Result | 逐明细/核验单元结论和整项汇总 | 分批写入、最终封存，保留历史 |

规则目录与发布包建议以核验业务库为权威来源，便于受理绑定和启用切换在同一个数据库事务内完成。Langflow管理页面通过受鉴权的管理入口操作它们。原生FlowVersion作为草稿历史和来源记录；业务发布包持有完整副本，不依赖跨数据库外键或草稿永远不被删除。

## 4. 对外输入、解析与受理

2026-09-29按用户明确的从0到1原则修订：直接将 `/api/v1/verification/tasks` 改为三项业务输入，不并行维护按detail_ids提交的试验契约，也不为此次变化增加v2兼容入口。例如：

```json
{
  "hospital_scope": "常州市第一人民医院",
  "settlement_time_range": {
    "start_inclusive": "2024-06-01T00:00:00+08:00",
    "end_exclusive": "2025-09-01T00:00:00+08:00"
  },
  "rule": "高值耗材智能体"
}
```

月份选择由监管页面转换成确定边界；开始/结束是同一个时间范围配置项。接口不接受依赖自然语言猜测的日期解释。

来源从鉴权凭据确定；监管后端每次新提交生成稳定的幂等键，网络重试沿用原键。相同来源和键、相同输入返回原任务；同键异内容返回冲突；使用新键可有意再次提交同样条件。幂等查找应先于重新解析当前启用版本，否则v1受理后重试可能误变成v2任务。

受理步骤：

1. 验证输入和来源身份，检查已存在的幂等记录。
2. 按登记表准确解析医院名称/别名或预定义范围标识，保存标准医院集合、结算机构编码、影像organ_code和映射修订。未知或歧义输入返回明确错误，并校验来源允许访问这些医院。
3. 将规则名称/别名解析为稳定编码，例如 `high_value_consumables`，校验已发布且在当前环境启用。
4. 在短事务中绑定当前发布包及环境修订，保存规范化范围、Task与首个Run；受理与版本启用切换需要明确的事务顺序。
5. 返回202和task_id/run_id、实际采用的版本。后台发现明细；受理接口不等待扫描十几个月的数据。

首期医院字符串按单院名称或已登记范围标识处理；尚未确定多院字符串语法，不自作主张按逗号、模糊匹配或大模型解释。规则优先支持稳定编码，兼容已登记的唯一中文名称。监管可查询平台规则目录，只保存选择值，不需要保存规则内容。

## 5. 发布、规则版本和启用

### 5.1 一份业务版本对应一份完整发布包

首期建议业务规则版本就是RuleRelease版本，例如 `high_value_consumables@1`。包内保留Langflow的flow_id和flow_version_id用于来源追踪，但不让使用者分别拼接“流程v3＋规则v5＋词表最新版”。原生流程版本号与业务发布版本号不是同一个编号。

发布包应包含：

- 节点类型、执行代码/组件标识、连线、全部生效的业务参数和输入输出契约。
- 医保目录映射、部位词表、分组与计数规则、比较项目/容差等内容或不可变版本引用。
- 子流程、外部文件等依赖的固定引用；首期无法固定的动态依赖禁止进入正式核验发布包，并在发布检查中具体说明。
- 结算/影像/模型适配契约版本、连接引用、可固定的模型标识和版本要求。
- 执行业务模块和依赖对应的构建标识或镜像摘要、内容摘要、发布人、发布时间和说明。

画布节点是节点业务参数的编辑来源，发布时编译成完整生效配置。目录等共享资源在平台维护，但必须选定版本。发布后不再从环境变量、TaskConfig或另一份可变policy覆盖同名规则；空URL等默认值应在发布/环境绑定时明确解析，不能留到运行时读取未固定的全局默认值。

凭据只保存受保护的配置引用，轮换凭据与改变规则是两类操作。节点直接配置的URL仍可编辑；修改草稿URL要重新发布才能作用于新任务。环境连接由有修订的绑定管理；改变机构映射、接口语义或模型版本需要明确的新绑定/发布流程，不能在运行中悄悄替换。

### 5.2 发布与启用分开

1. 从确定的草稿快照准备发布候选，执行结构、参数、依赖和模拟验证；验证结果绑定同一内容摘要，防止验证后改图再发布。
2. 复用原生版本快照能力记录编辑来源；把确切快照、资源和摘要保存到业务发布包。准备过程可跨服务，数据库事务不跨HTTP调用。
3. 在业务库事务内写入只读发布包。发布失败不能修改正在使用的启用关系；按发布请求标识处理重试。
4. 首次发布或升级经“启用此版本”动作更新该方案/环境的指针。采用期望修订号防止并发管理员覆盖，记录启用历史。

发布成功不必立刻接新任务，便于先验证再启用。草稿保存不会发布；发布不会自动升级既有任务。可提供“发布并启用”的组合操作，但后台仍执行上述校验和原子切换。

### 5.3 生命周期规则

| 操作 | 对新任务 | 对已受理任务 |
|---|---|---|
| 编辑或保存草稿 | 无变化 | 无变化 |
| 发布v2但未启用 | 继续绑定v1 | 保持原绑定 |
| 启用v2 | 绑定v2 | v1任务仍执行v1，包括尚未开始的任务 |
| 回退启用v1 | 后续绑定v1 | v2任务不被改写 |
| 停止接收该方案的新任务 | 明确拒绝受理 | 默认继续完成已有任务 |
| 因错误撤销某发布包的执行资格 | 不再接收 | 禁止新的执行/后续模型请求，按停止确认流程处理在途请求；不偷偷换版本 |

内容不可修改，启用/停用属于单独的运行策略和审计记录。被任务引用的发布包禁止直接删除；删除草稿或原生历史清理不应删除发布证据。旧版本所需运行包不可用时明确报告不可执行，不自动用新代码替代。

## 6. 固定版本必须落实到运行入口

仅在Run多加release_id仍然不够。如果Worker继续调用会读取当前草稿的旧路径，记录的版本与实际执行内容可能不同。

建议增加受控的发布运行入口，复用Langflow图执行、组件策略和后台Job设施：

1. Worker按run_id请求执行；平台从受理记录验证release_id和环境绑定，不信任客户端任意上传的图。
2. 加载不可变发布包，校验摘要和运行包匹配，把包内图作为本次明确的执行数据传入现有图构建链路。
3. 拒绝业务任务通过tweaks、全局变量、局部起止节点覆盖发布规则。凭据和约定的任务上下文通过专门通道注入；首次实施检查所有默认值、子流程解析和缓存路径。
4. 缓存至少按发布内容摘要和运行环境区分；核验节点的副作用不能通过“冻结节点”或旧构建缓存跳过。当前按可编辑flow_id的缓存不能直接复用到不同发布版本。
5. 返回平台job_id并记录至Run。排队后、进程重启后都从同一发布快照恢复尚未开始的作业输入，不能重新读取草稿。

不采用每次执行前activate旧快照的方案：activate会改写共享草稿，并发v1/v2任务会互相干扰。

平台后台Job与业务Run明确关联，按run_id建立长期唯一的执行登记。同一Run的请求即使在Job终结后重试，也只能查询原Job；不能只依靠当前原生“未终结Job去重”。登记、任务排队及回执之间的中断窗口须有可查询记录，单纯收到网络超时不重新提交。

后台运行解决长HTTP请求问题，不等于业务自动恢复。现有后台服务会重新排入未开始的QUEUED任务、将失联执行标记失败；需要按核验语义接入。已开始且模型受理状态未知的核验仍进入needs_confirmation。首期不自动重试模型或重跑整个图。全局Job成功还须核对08的业务保存回执，不能代替业务完成条件。

## 7. 批量处理：保留00—08，改为引用与分批落库

首期建议一个业务Run对应一个完整图作业，阶段仍顺序执行。每个阶段内部按页/核验单元读取数据库并保存工件，输出只传 `task_id/run_id/release_id/snapshot_id/manifest_id` 等引用和小型统计。

这是有界内存的阶段处理，不是把整个旧图按每页重复运行，也不是Worker逐个调用业务节点。首期不承诺百万条数据吞吐或任意节点续跑；单作业耗时预算、数据量上限和背压通过实测确定。长阶段在批次边界检查停止状态并更新心跳/进度。

| 节点 | 调整后的职责与边界 |
|---|---|
| 任务输入 | 引用已受理任务；画布调试选择模拟任务，不能随意填未登记的业务范围直写结果 |
| 00任务入口校验 | 校验任务、当前运行、执行登记、模式和发布版本；加载已固定范围。无需监管提供明细ID，不再次解析“最新版” |
| 01结算快照 | 按标准医院及医保结算时间分页查询；核对返回范围、字段和重复记录，落库快照与实际明细清单；全部页成功后封存，返回引用 |
| 02耗材筛选 | 分页筛选，保存入选/排除原因；在完整清单上按患者、医院、就诊、类别、侧别、单位及已验证计数口径组织核验单元 |
| 03检查关联 | 按单元内结算关联条件调用检查列表，取得study_primary_id及元数据；检查窗口不增加范围外结算 |
| 04部位初筛 | 应用本发布包的字段和词表，保存命中及保留待核实原因 |
| 05影像清单 | 按study_primary_id查序列，再按series_id查影像URL，保存单元证据；不在节点下载DICOM |
| 06模型识别 | 对核验单元登记请求后调用固定契约的模型服务，保存实际处理范围、原始返回与模型版本；异常不能补0 |
| 07确定性比较 | 使用固定规则和事实依据比较，保存单元结论及逐明细关联；缺覆盖或计数依据则未比较 |
| 08结果保存 | 分批提交逐明细/单元结果，核对已封存清单及终态覆盖，最后在短事务内封存汇总并完成Run |

分页是技术处理单位，核验单元是业务比较单位，两者不能混用。同一就诊的耗材明细跨两个查询页，仍需按稳定分组键聚合，不能对同一影像数量比较两次。首期先完成01全量发现再完成02分组，降低边读边分组造成遗漏的风险。过大的业务单元需要明确上限/未比较原因，不能为凑批次大小随意拆开计数范围。

阶段03—07可保存各单元成功、明确失败、未比较的状态；基础设施故障和未知模型受理状态另行中断/待确认。08输出分页可读结果，整项完成必须满足所有应处理明细都有明确去向，不能把“第一批成功”当整项成功。汇总按单元计数并去重，不能把共享单元的差异金额随明细复制后再次求和。

发布校验对本核验方案要求入口、范围冻结、必要业务阶段及保存闭环连通，存在合法的无数据/排除路径。Verification节点仍可自由拖拽用于搭建调试；绕过必要阶段的草稿不能作为正式核验发布包。

## 8. 数据范围、事实依据和结果口径

### 范围查询接口

新结算适配器至少需要医院编码集合、明确时间字段和边界、稳定游标/排序、分页结束标识。返回需包含稳定明细键、真实SETL_TIME、关联患者/就诊字段、耗材目录、数量/单位/单价/金额等原有业务所需字段。

01按已绑定医院映射查询；本地再次检查范围。范围外或无法确定结算时间的数据不能进入本次结果，记录接入错误及数据完整性状态。已有报告的SETL_TIME缺口必须接入真实字段，UPDATE_TIME不能替代。

查询期间源数据可能变化。优先要求源系统提供快照标识、稳定导出或等效一致性能力，并记录获取时点。若接口只支持普通分页，本地封存只能保证“这次实际取得的数据不再改变”，不能宣称取得某一时点的全量一致快照。发现分页中断、同键异内容等异常不得标记范围发现完成；数据一致性能力是实际联调的验收项。

### 事实依据

原受理参数reviewed_scopes不仅是配置，包含哪些明细、检查可比较及覆盖/计数核实信息。新监管输入不再携带这些事实。建议从平台核实记录或已验证的模型能力/数据关联记录加载，按本次Run固定其证据来源和版本。

不能把target_confirmed、coverage_confirmed、counting_validated在规则里统一设true。缺依据仍可完成数据关联和保留识别输出，但数量/费用结果应标为未比较并说明原因。用于联调的核实记录继续明确标为模拟。

### 结果与状态

任务执行状态与业务结论分开：执行完成可包含不适用、未比较和差异。无范围内结算为“完成，无匹配数据”；不是“所有耗材核验一致”。数据有缺漏为失败或带明确不完整标记的部分结果，不宣传已核验完整范围。

结果至少关联：原始条件、规范化医院/结算范围、rule_code/release_id、图摘要、执行包/绑定修订、run/job、结算快照、核验单元、影像证据、模型请求/返回及逐明细结论。差异仍是人工复核线索。

阶段进度展示“已发现明细数、发现是否结束、已筛选数、核验单元数、各阶段已处理/失败/未比较数”。01未完成时分母未知，不以当前页数计算虚假的总进度百分比。

## 9. 版本更新与重跑示例

例：方案当前启用v1；任务A在10:00受理医院和2024年6月—2025年8月结算范围，绑定v1。10:05修改02节点筛选条件并发布启用v2。10:10才开始执行A，仍使用v1；此时新受理B使用v2。A的所有分页、阶段、单元均沿用v1。

重跑必须区别三种动作，均新建Run并保留原记录：

| 意图 | 数据 | 规则 |
|---|---|---|
| 默认重新执行 | 优先复用原已封存的结算快照与固定明细；其他证据来源明确记录 | 原发布包 |
| 使用新规则重新核验 | 同一份已封存结算快照便于对比；未保存的外部证据需重新取得并记录 | 操作时明确选择的已发布版本 |
| 重新查询范围并核验 | 按原医院/时间范围重新查询，生成新快照，明细集合可能变化 | 明确记录选择原版本还是当前启用版本 |

首期可只开放默认同版本重跑，后两类在Run模型预留清晰语义，按实际需求开放。原01未完成或无封存快照时，重新取数必须明确标记，不能称为复用原数据。若需严格重放，必须另行保存足够的影像输入和固定模型/运行环境；当前保存影像URL不能保证将来地址仍有效，也不能保证外部服务永远返回同样结果。

任何新Run开始前须确认旧执行不再进行。停用新任务、取消Job、停止远端模型是不同动作，不能因为本地状态改成failed就认定远端已结束。旧Run迟到回写不得覆盖新Run。

## 10. UI与代码改造范围

平台增加规则管理入口：方案目录、关联草稿、发布候选检查、发布历史/只读查看、当前启用版本、启用/停用和回退。复用画布和原生版本浏览，不把全部任务管理塞进节点。发布和启用需要平台管理权限及审计；最低实现使用现有管理员身份约束，不依赖默认放行的可选RBAC服务保证发布权限。

画布明确区分“编辑草稿”和“查看已发布vN”；00展示任务/范围/版本摘要，01配置受控结算数据源/字段映射引用并展示查询统计。医院和月份属于每次任务输入，不固定写在节点中。02—07仍编辑业务规则与API连接；发布历史只读，需要修改时回到草稿形成新版本。

监管页面继续只有三项业务配置，查询任务进度和分页结果；平台返回实际采用的版本供追溯，不要求监管维护规则详情。正式业务提交与Playground模拟调试使用不同模式/受理入口，防止修改草稿影响正式任务。

| `verification/worker.py` | 领取后请求发布快照后台执行，保存job关联、查询状态并核对08保存；保留未知状态不重提原则 |

验收场景至少还包括：正式模式拒绝模拟绑定；同一单元不因分页重复识别或计算金额；08分批保存中断不显示整项完成；业务完成与Job终态不一致可定位；历史正式发布所需运行包缺失明确失败；重跑保留原结果。已有测试中仍符合目标的业务规则与失败处理用例保留，试验契约和兼容用例直接替换或删除；新契约单独验收。
