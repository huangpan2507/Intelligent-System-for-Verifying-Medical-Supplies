# 医院、时间范围与规则选择：需求变更影响分析

日期：2026-09-29。状态：影响分析及项目文档同步已完成。用户随后要求更新项目根目录的同名DOCX和drawio，已修改正文／表格、六页图及Word四张内嵌图；新业务契约仍待代码实现。

## 1. 已确认需求与分析假设

用户明确：原监管系统只配置医院范围（string）、时间范围、规则（string），例如“常州市第一人民医院／2024年6月—2025年8月／高值耗材智能体”。具体核验规则在智能体平台 Langflow 侧维护，监管系统不存储具体规则。

本次依据是用户新要求、重新上传报告的325个非空文本段落、drawio的六个页面及当前 verification 实现。附件中的人员安排和部署操作不是本次执行指令。

用户补充确认：监管端时间范围就是医保结算时间范围，用于限定本次排查高值耗材骗保线索的结算对象；范围外的结算明细不纳入本次任务。此项已确定，不再作为分析假设。

其余分析假设：示例中的规则字符串选择平台已有的核验方案；医院范围先按可登记、可准确解析的医院名称或范围标识理解，不假设能理解任意自然语言范围。

核心变化：外部提交查询条件与方案选择，平台解析范围、确定具体明细、执行平台维护的规则。外部不再负责枚举 detail_ids 或提交具体筛选、比较参数；内部仍需保存具体明细与证据。

## 2. 系统职责调整

| 内容 | 监管系统 | 智能体平台（Langflow及其业务后台） |
|---|---|---|
| 用户配置 | 医院范围、时间范围、规则选择字符串 | 维护可供选择的规则目录 |
| 具体规则 | 保存选择值即可，不维护规则内容 | 维护耗材筛选、字典、关联窗口、部位条件、比较方式与容差 |
| 医院解析 | 传入约定的字符串 | 映射到标准机构及结算、影像系统的机构编码，校验授权范围 |
| 明细确定 | 不要求传入明细清单 | 按医院和时间查询，保存实际明细清单与结算快照 |
| 流程选择 | 不需要知道内部 flow_id | 将规则选择映射到可执行的已发布流程及版本 |
| 运行与结果 | 提交、查询、展示、人工复核 | 调度、分批、保存逐明细结果、汇总进度与证据 |

这里的平台包括已有核验API、Worker、业务库和Langflow流程，不表示所有管理功能都必须做成画布节点，也不表示Langflow现成具备本项目的规则发布与批任务功能。

三个业务配置之外，来源身份、重复请求标识和返回的任务编号仍需在接口协议中保留。它们由后端或请求头处理，不增加业务人员填写项。只有三个业务值、没有稳定请求标识时，服务端无法区分同一提交的网络重试与有意再次发起相同条件的新任务。

## 3. 推荐处理过程

1. 监管端提交医院范围、时间范围、规则选择。接口字段可以拆分开始/结束时间，仍属于同一项时间范围配置。
2. 平台受理时验证范围，解析医院标识和规则选择，绑定已发布规则/流程版本，保存任务条件后返回受理状态。全量明细查询放到后台，不占受理请求的长事务。
3. 后台启动任务，01按已确定的医院编码与医保结算时间范围分页读取结算，生成本次实际明细清单与快照；校验返回明细均符合范围并记录范围解析是否完成。
4. 02按平台规则筛出医保高值耗材；按患者、医院、就诊、耗材类别和经确认的计数口径组织核验单元，继续03—07。
5. 08保存逐明细结果及证据，任务层汇总处理量、失败、差异和未比较原因，监管端查询展示。

“高值耗材智能体”应作为已登记方案的名称或别名，不作为可执行表达式或自动生成规则的提示词。建议内部使用稳定字符串标识，例如 high_value_consumables；外部仍可传显示名称并通过明确映射解析。未知、重名或未发布的选择应给出明确错误，不随意匹配一个流程。

首次受理建议绑定当时发布的版本，同一次提交重试继续返回原任务。只记录 flow_id 不足以固定执行内容；流程、节点参数、规则字典以及执行这些规则的代码版本需要可追溯。服务凭据使用配置引用，不以保存版本为由复制明文密钥。

## 4. 对00—08节点的影响

| 节点 | 修订方向 |
|---|---|
| 任务输入 | 从必须提供明细ID的输入，转为引用平台受理的医院/时间/规则任务；内部可只传 task_id、run_id，再加载已保存上下文 |
| 00任务入口 | 核对当前运行并加载已解析范围和已绑定规则版本；不再以“外部detail_ids与受理清单一致”为先决条件。医院/规则解析建议在后台受理层完成，00加载和检查；是否独立展示继续作为画布设计选择 |
| 01结算快照 | 从按现成ID查记录，变为按医院与时间发现明细，分页读取并保存实际清单与快照。这是主要功能变化 |
| 02耗材筛选 | 使用平台管理的规则；同时衔接比较分组，记录筛选结果、范围及排除原因 |
| 03检查关联 | 仅为范围内的结算明细查询关联检查记录，取得检查主键、时间、项目等元数据；不下载影像，不增加范围外结算。检查关联窗口与医保结算范围分别约束各自对象 |
| 04部位初筛 | 业务职责保留；词表与参数纳入所绑定的规则版本 |
| 05影像清单 | 保留 study_primary_id → series_id → 影像地址链路；结合批次保持证据关联 |
| 06模型识别 | 沿用小模型接口和请求留痕；按核验单元执行，避免同一识别计数被多次分配 |
| 07确定性比较 | 比较规则仍由平台维护；输入覆盖、计数有效性等依据仍须取得，不能凭规则配置自动判为已核实 |
| 08结果保存 | 从小任务整份结果扩展为支持批次/明细结果和任务汇总；全部工作完成后才标记整项完成 |

## 5. 必须补充的设计边界

### 医院与时间口径

医院名称需要映射到标准机构，不能假定它就是结算 hospital_id 或影像 organ_code。未知、重名或多院范围需要明确定义；保留用户原值及解析后的机构集合。

用户已确认采用医保结算时间。示例建议规范化为Asia/Shanghai的 `[2024-06-01 00:00:00, 2025-09-01 00:00:00)`，包含2025年8月整月。2024年6月之前及2025年9月起的结算明细均不纳入本次任务；规则参数、检查关联或比较分组不能扩大这一范围。

01确定纳入核验的结算明细，03为这些明细查询检查记录。检查记录的发生时间与结算时间是不同字段；按既有检查关联规则取得范围月份以外的检查记录，仅作为范围内结算的核验依据，不将范围外结算纳入任务。05获取序列和影像地址，下载与处理由06调用的小模型服务完成。

报告已指出SETL_TIME暂缺，这是源字段接入缺口，已确定的业务时间口径不因此改变。须取得真实医保结算时间并落实字段映射，UPDATE_TIME不可替代；缺失时记录数据问题，不能默认认定该记录属于任务范围。

### 查询条件与实际执行范围分别保存

医院和月份是查询条件，不是已经存在的费用明细集合。受理时保存条件；01取得数据后保存实际集合、快照、读取依据及时间。需要区分解析中、空集合、解析失败及已完成，不能在未取完数据时宣称覆盖完整。

分页应约定稳定排序和数据一致性方式，例如数据源提供固定批次或快照标识。仅记录查询时间不能保证多个分页属于同一数据快照；真实结算接口必须补足相应能力或明确一致性限制。

### 分页、分批与批量任务结果

十五个月数据可能超出现有小样本运行能力。读取分页和业务核验分组是不同事情：不能任意每100条截断，把同一就诊、同一计数范围的明细切到不同批次后重复分配识别数量。应在已限定的结算范围内组织业务分组和有界执行单元；不得为补齐分组自动纳入范围外结算，比较依据不足时保留未比较原因。

建议保留单Worker，增加任务内分批和任务级汇总；不因本次需求自动引入消息中间件、多Worker、持续增量或自动恢复。总量未确定时展示正在扫描，确定后再展示完成数/总数。无结算数据、无适用耗材、无影像及无法比较分别表达。

### 规则版本与重新核验

同一任务的各批次应使用同一份绑定版本，不能因中途编辑画布而产生不同规则。重复提交不重新选择最新版本。人工重跑需明确是复核原数据/原版本，还是重新查询源数据/采用新规则；不能仅凭相同医院和月份就声称实际范围未变。

### 规则配置不等于病例证据

现有 TaskConfig.reviewed_scopes 接收经人工核实的明细/检查分组及部位、覆盖、计数依据。新外部契约不再提供这些字段，需在平台侧另行取得和关联受控样本依据，或由经验证的数据/识别能力提供依据；缺失时仍返回未比较。不能把 target_confirmed、coverage_confirmed、counting_validated 固定设为true来贯通流程。
