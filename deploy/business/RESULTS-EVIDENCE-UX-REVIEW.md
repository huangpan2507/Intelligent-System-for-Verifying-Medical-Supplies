# Results 证据查看与保存信息的展示设计

日期：2026-10-15。范围：髋膝关节正常核心流程（数据库＋API，精简11节点）的 Results，以及使用同一组件的任务结果页。

状态：Q57—Q59 已实施，运行画布与中文任务结果页的只读验收已通过。用户已同意 Q57“宽弹窗，业务摘要优先”、Q58“保留业务摘要，技术详情下沉”、Q59“按业务关联展示，可查原始记录”。本轮增加只读证据查询与结果展示，不修改数据库表结构、既有结果或11节点执行拓扑。

后续展示简化：按用户确认，默认结果表格移除“识别减结算”差值列，仅展示“核验事项／结算侧／识别侧／结论”。节点预览和任务结果页共用此表格；Compare 的差值计算、结果落库、中文说明和保存详情中的差值仍然保留。

## 改造前的约定与问题

- Q52—Q56 已实施：模板约定必要留存，中文说明读取实际比较结论，逐条结果和证据关联落平台库，普通使用者不配置覆盖关系。
- 上一轮已移除外层只有说明文字的“来源与证据”分组。Results 外层当前为结果模板、结果预览、保存与完整性；真实证据入口仍在每条实际结果卡片内。
- 当前证据列表将所有来源、识别调用和影像平铺，主要用内部编号或同一申请单号作为标题。
- 来源引用展开后只显示数据集编号与内部行号，没有直接呈现所引用记录的内容。
- 请求/响应按钮读取已保存记录，但 JSON 显示在整个列表末尾，按钮处缺少明显反馈。
- “保存与完整性”中的44项字段名挤成一段，覆盖声明则直接展示 JSON。两者是保存约定的技术表达，不是用户需要填写的配置。

## 实现事实与含义

| 现有内容 | 实际含义 | 不能由它推出的结论 |
| --- | --- | --- |
| Original source 的数据集编号与行号 | 某条来源快照的定位引用 | 当前界面已经展示该条记录内容；它是医院原始主键 |
| 多个相同数据集编号 | 可以引用同一数据集的不同行 | 必然是重复数据，可以删除 |
| Image source 中的申请单号 | 影像来源所关联的申请单 | 同号就是同一检查或同一张影像 |
| Recognition call | 平台保存的一次识别调用 | 点击查看会重新执行识别 |
| 保存区域44项字段名 | 当前结果模板要求留存的属性名称 | 某条实际结果已经有全部值，或者整个任务已交代完整 |
| 保存区域 Technical details JSON | 模板提供的来源范围、核验事项与去向约定 | 本次执行已经满足这份约定 |
| 结果卡片下的技术 JSON | 某条已经保存的实际结果、字段值和模板版本 | 当前草稿模板就是这条历史结果的模板 |

已核对的膝关节样例中，证据列表16条包含：1条结算来源、2条检查来源、2条序列来源、5条影像接口返回行、1次识别调用、5条逐影像来源。接口返回行与逐影像来源承担不同追溯作用，展示整合不能将它们再计成10张影像，也不删除后台关联。

来源记录已在任务的数据集中留存。当前公开的读取接口仅支持 limit/offset 分页，没有按内部行号精确读取；不能把内部行号当分页偏移量。证据接口的 total 是该结果全量证据关联数量，不是每组业务对象数，前端当前页也不能用于推导全量分组数量。

## Q57：识别请求与响应弹窗（已同意）

已确认点击后打开可关闭、可滚动的宽对话框，而非鼠标移开即消失的悬浮提示。

- 默认展示调用所属核验对象、影像数、状态、返回类别和数量、模拟标记；只表达实际存在的请求或响应内容。
- 分“发送内容／返回结果”查看，底层 JSON 放入技术详情。
- 加载、失败、未收到返回均在当前弹窗内显示，不能让用户去列表末尾寻找。
- 关闭后回到触发按钮，不改动结果、不再次调用服务、不发起新的工作流任务。
- 复用现有请求记录和任务访问边界，不新增权限系统或影像诊断查看器。

## Q58：保存与完整性分层（已同意）

已确认保留中文业务摘要，将技术信息放入按需打开的只读详情。

| 层级 | 已确认的展示方式 |
| --- | --- |
| 普通页面 | 保存范围的中文说明、实际保存状态、需要注意的漏处理与未完成事项 |
| 留存字段详情 | 按原结算、分类、识别、计算比较、影像与追溯分组；使用中文含义＋字段名的表格，不再拼成一段文本 |
| 技术诊断 | 当前查看对象对应的模板版本、内部标识、覆盖声明、原始结构化结果 |

必须区分无实际任务时的“约定”与所选任务的“实际结果”。本条三项比较一致、当前结果已保存、任务执行结束、全范围结果已交代是不同事实，不能互相替代。实际任务按当时保存的版本与评估展示；不能用当前草稿的配置为历史任务补出“完整”或“已保存”。

从普通页面移走字段清单与覆盖 JSON 不影响落库和追溯。后台的44项留存、来源关联、识别请求保存、发布检查和执行覆盖核算继续存在；不将隐藏技术细节实现为关闭检查。实际缺口、不可用来源或失败仍要可见。

## Q59：来源与影像展示（已同意）

用户同意“按业务关联展示，可查原始记录”。每条结果的证据区分为“结算明细”“关联检查与影像”“识别调用”；检查之下展示序列、序列之下展示具体影像。用户不需要维护这些分组和关联规则。

- 用业务分类和来源名称替代内部编号作主标题，内部编号留在技术详情。
- 优先显示结算明细，以及检查、序列、具体影像之间的真实对应关系；识别调用单独展示。
- 点击来源记录读取任务当时保存的快照，默认展示业务关键值，并允许查看完整留存字段。不重新访问医院源库来替代历史记录。
- “完整留存字段”指当次查询实际返回并保存的内容，不把查询投影后的结果称为源数据库整张表的全部字段。
- 原始接口返回行可以成为对应影像的来源详情，不必再作为一个难以理解的顶层 Original source 条目。
- 同一申请单可能有多项检查、多条序列与多张影像。层级必须依据已保存的医院/系统/检查/序列/影像标识建立，不能按相同申请单号或列表顺序猜配。
- 缺失标题字段时保留实际标识，不编造检查名称、时间、文件名或影像序号。来源无法读取时明确提示，不能用另一条记录填补。
- 分组与统计需覆盖全部证据；列表分页、按需加载不能把当前页数量冒充全量数量。
- 影像清单沿用 Images 已约定的完整地址去重口径，本轮不重新定义影像身份或去重策略。同一清单项可对应多条原始返回记录；展示这些来源不额外增加影像数量。

### 接口核查结果与必要补充

- 核心来源实际包含 Settlements、Studies--source、Series--source、Images--responses。业务分组应基于已保存的来源角色和元数据，不只匹配节点显示名称或假定固定编号。
- 当前 image context 已留存医院/系统、检查标识、序列标识、地址与 DICOM 三级 UID，可以支持正常结果中的影像层级；但没有直接包含每张影像对应的来源数据集/行引用。
- API 原始行已有 `_request_row_id` 和来源父数据集关系，底层行来源关联也仍存在。应由后端解析这些已保存关系，给出具体来源引用，再供界面查看，不能用相同 RPT_NO 或顺序拼接。
- 需要精确读取某个结果实际引用的来源快照：验证任务访问权、结果归属、数据集归属及证据关系，再按内部行号查询；不能用分页 offset 冒充行身份。
- 需要全量分组数量和稳定分页，保留接口原始行与逐影像来源的不同角色，不混计业务对象数量。
- 既有识别请求读取接口返回保存的 payload、response 与调用状态，属于只读查询；宽弹窗可以复用该接口，不新增识别执行路径。
- 请求接口当前校验任务及请求归属，并不校验结果级关联。结果中的按钮应绑定其真实证据引用；如新增结果级详情接口，沿用该关联校验。当前请求记录未单独保存服务地址，不能拿当前连接设置冒充当时调用目标；能从任务固定配置确认的信息才展示，未留存的内容不补造。
- 当前未到达最终 Results 的对象，可能只关联到早期核验对象的来源；缺少检查或识别证据引用不能被表述为“这次任务从未查询或调用”。本轮先验收正常核心结果，不扩展未完成任务的全部证据重建，界面如实提示“当前结果未关联”或“未提供”。
