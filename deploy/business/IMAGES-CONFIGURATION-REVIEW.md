日期：2026-10-15。范围：髋膝关节正常核心流程（数据库＋API，精简11节点）的 Images；底层能力为通用 Business API。

## 已核实的业务含义及运行配置

- 耗材明细是一项具有业务身份的来源明细，不是字段，不是患者，也不是一张影像。当前身份由 ORGAN_CODE、DATA_SOURCE、SETL_FEE_LIST_ID 共同确定；相同明细的重复来源记录由 SettlementChecks 处理。
- 一条明细记载 CNT=2，仍可以是一条明细；关联多个检查与序列不会增加原收费数量。
- 来源明细进入流程后，节点会增加身份、分类、关联和判断字段。字段保存在流程数据集中，不会因此自动给原数据库加列。
- 当前结算表 public.core_flow_settlement_v1 共51列。Images.retain_fields 明确列出58项：全部51列及 target_category、classification_method、classification_reason、classification_evidence_field、classification_evidence_text、classification_confidence、_representative_row_id。分组键 _identity 另外保留。这是已配置快照，不是自动保留未来全部上游字段。
- Images 从每条 Series 输入记录的 series_id 构造 API 请求；本节点不读数据库。原始API结果可能扩展成多行，随后按 _identity 归集回耗材粒度。
- 地址按 domain + file_path 原样拼接，同一明细内按完整地址去重；查询签名不同的地址不会因此被认定为同一影像。三个UID要求非空并写入逐影像来源，不等同于已实现基于UID或影像内容的完整去重。不同明细可各自保留同一影像。
- 实施前 item_context 不含 RPT_NO；RPT_NO 在顶层58个保留字段中。Observation 不单独发送顶层 RPT_NO，逐影像上下文因而也未携带该字段。本轮已加入并核对实际 Observation 请求。
- Images 输出是数据集引用，记录中的 image_manifest 与 image_manifest_context 为JSON数组文本。Observation 映射到 evidence、evidence_context，当前模拟识别服务显式解析；不能保证任意外部服务自动接受该序列化约定。
- 最近核对时草稿请求与字段证据的 url_type 均为3。此前出现过0与3不一致，但不将旧状态当作当前问题；实际实施前须再核对最新草稿。

|---|---|---:|
| A | 髋DR | 2 |
| A | 髋CT | 3 |
| A | 近髋DR | 2 |
| B | 膝DR | 2 |
| B | 膝CT | 3 |

## 技术配置的实际作用与删减边界

| 项目 | 当前作用与必需性 | 删除或留空的影响 |
|---|---|---|
| Cursor path / Cursor parameter / Page parameter | 分别指定下一页游标所在响应路径、游标请求参数和页码请求参数；当前pagination=none，不使用 | 当前可不填；界面应按分页模式显隐。不可据此删除通用API分页能力 |
| Completeness.basis | 来源完整性约定的说明；当前为受控模拟每次请求返回完整有限集合 | 不是文字即证明。保留对象但清空必填值不合法；删掉整个完整性约定会令来源完整性未知并影响下游处理 |
| Completeness.scope | object表示每条上游记录发起的独立请求；当前是序列请求，不是归集后的原耗材 | 会影响失败范围处理，不是纯显示字段，不应静默更改 |
| Completeness.complete_path | 可选响应布尔标志路径，配置后要求响应值为true；当前未配置 | 当前可空；不应自动猜测，也不能把has_more直接当成完整性确认 |
| Object context fields | 在API原始记录上复制上游字段，带_context_前缀；当前为空 | 当前可不填；与collection.item_context不同，不能合并成同一个配置值 |
| API business success conditions | 当前code=数字200、error.error_code=数字0 | 移除会失去这两项业务成功检查；HTTP成功本身不证明业务成功 |
| Collect by source record | 当前按明细形成清单，生成Observation依赖字段 | 对通用API可选，对本流程必要；直接删除会改变输出粒度与结构 |
| API output fields | 当前消费domain、file_path和三个UID，真实模拟响应另有三个字段 | 删除结构声明会使字段引用与响应校验失去依据；可由契约、结构文件、实际样本提供 |
| Provider contract | 字段结构、来源引用和请求绑定；当前依据是文档 | 普通搭建者无需重填已有效的契约，但不能删除依据后宣称仍已验证 |
| Test request and discover fields | 显式发一次测试请求并确认样本字段 | 不是每次运行的必做步骤；单次预览不验证聚合、多对象完整性或识别能力 |

截图中必填星号表示配置对象的结构要求，不等于每个业务使用者必须从零手工编写。模板预设可以满足要求，运行校验仍需保留。

## 已确认的UI方案（Q44）

实施前UI核查：CanvasConfiguration 的宽编辑白名单没有api；Images仍走通用SchemaForm，三个分页参数没有按分页方式显隐。collection已折叠，Completeness等仍按后端结构排列。fields/field_evidence已从通用表单过滤，由ApiFieldConfiguration专门编辑，不把“重复字段编辑”误写成当前缺陷。

复用现有分组、摘要、紧凑编辑与宽面板。Business API继续通用，不新增只能用于影像的节点类型，也不在本轮新增接口注册中心、权限角色或自动猜协议能力。

| 业务分组 | 主区内容 | 按需展开的技术内容 |
|---|---|---|
| 1. 连接哪个服务 | 连接、接口用途与请求摘要 | 路径、GET/POST；保留明确可编辑入口 |
| 2. 用哪些信息请求 | 参数名→上游字段/任务参数/固定值的紧凑映射 | 复杂请求结构编辑，保留原JSON内容与类型 |
| 3. 如何确认返回有效且取齐 | 响应列表路径items_path、业务成功条件、完整性约定摘要、分页方式 | 成功条件编辑、basis/scope/complete_path；分页模式对应的参数、max_calls/max_pages限制 |
| 4. 如何整理成业务结果 | 启用归集、归集身份、地址构造、保留字段摘要 | 58项字段多选、逐项来源字段、UID及输出名称；未启用归集时仍可输出原始API记录 |
| 5. 返回字段与来源依据 | 字段数、契约来源、有效/待确认状态 | 文档字段、结构文件导入、响应结构编辑 |
| 6. 测试与输出 | 显式测试入口、输出粒度与Data/Issues说明 | 测试上游记录、参数、响应样本、输出字段详情 |

成功和完整性摘要不可全部藏入无提示的高级配置。协议编辑入口是信息层级，不代表已经新增权限隔离。折叠错误可见并可展开；更换连接或请求时显示字段依据失效，不静默重新认可；新通用节点没有有效预设时必须明确指出待配置项。

Object context fields放在返回记录的可选追溯详情中，明确区别于归集结果的逐影像来源。API output fields只保留一处主要结构编辑，避免通用表单与契约区重复编辑同一份字段；测试样本可以另有待确认结构，不自动覆盖已保存契约。

删除response_conditions还会改变字段依据绑定的请求定义，需要重新确认契约；不只是减少一项运行检查。Object context fields当前为空可隐藏，但通用流程若已使用_context_列，不能静默删配置。分页参数缺省名仅是协议默认值，不代表删除自定义参数名总是等价。

## 实施约束

- 六组表单编辑同一份画布配置。隐藏分页及技术输入只改变显示，不删除已存值，不在展开、收起或切换宽度时重新生成默认配置。
- 保留字段摘要根据实际配置及可确认的字段来源生成。当前模板可显示“结算表51字段＋7个分类及追溯字段”；其它来源或元数据未就绪时显示实际已选数量与来源待确认状态，不伪造51＋7的固定说明。
- RPT_NO仅加入本流程的逐影像上下文字段列表，通用API节点不强制所有业务使用该字段。顶层已有RPT_NO继续保留，Observation沿现有evidence_context映射传递新增内容。
- 同步维护核心模板、创建或更新模板的脚本及当前运行画布，避免重新生成模板时丢失RPT_NO。应用前读取最新草稿并备份，只更新本次目标字段，不用历史快照覆盖用户的新配置。
- 如新增上下文改变执行包，按现有发布机制核对并同步实际启用版本；不直接改写历史任务结果，也不把未发布草稿称为已运行版本。
