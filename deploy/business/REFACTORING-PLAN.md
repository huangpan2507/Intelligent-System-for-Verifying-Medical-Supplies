## 2. 沿用的目标和约束

以下来自此前用户提出的实施范围及本轮讨论，不重复作为新增决策征询：

1. 平台面向通用数据处理与业务核验；业务名称、医院和耗材类别不能成为核心执行器的分支条件。
2. 数据库读取与 API 读取是不同节点类型，同一流程可有多个实例并混合使用。“数据读取类节点”是职责分类，不是一个包办所有协议的节点。
3. 数据库首期支持 MySQL、PostgreSQL；可视化配置优先，复杂取数允许 SQL。
4. 保存本次查询范围内返回的原始记录和原始字段；高级 SQL 未返回的字段不属于已保存内容。
5. 按百万行任务设计，分批处理、持久化数据集、分页展示。具体容量通过指定夹具和资源测量验证。
6. 保留版本固定、来源隔离、未知状态和原始依据；任务执行状态与业务结果分别展示。
7. 以跨库对比和高值耗材两个场景验证通用性；模拟标记必须保留，模拟不能证明真实影像准确性。
8. 保留既有历史任务和结果；旧固定流程停止接收新任务。
9. 当前范围为单部署；不引入源业务库写入、持续人工审批等待、分布式大规模执行或自动恢复系统。

## 4. 已确认的决策记录

### D01：最终业务去向核对，是否由业务方案声明

**状态：已确认，2026-10-10 用户选择 A。**

决定：由业务方案声明是否需要逐对象交代最终结果。普通处理方案可只约定目标输出；核验方案必须声明核验对象和事项，并交代结论或无法得出结论的原因。该约定由流程设计人员配置，随发布版本固定；外部调用方不能在单次任务中关闭它。两类要求共用平台的节点与执行机制。

保留的共同约束：原始数据留存、错误和未知状态不冒充有效结论、技术执行与业务结果分开。

对照场景：

- 普通数据处理：从 10,000 条订单中筛出 100 条符合条件的记录，业务只需要这份清单。
- 业务核验：对约定的 100 个业务对象逐一核验，需要交代每个对象的结论，或未比较、排除、问题原因；不能仅输出其中有结论的对象。

| 选项 | 具体行为 | 代价和收益 |
|---|---|---|
| A：按方案声明，已选择 | 普通处理方案约定输出数据；核验方案声明对象、身份和核验事项，并逐对象交代结果。由流程设计人员配置并随版本发布，外部调用方不在单次任务中关闭该要求 | 保持通用性；需要清晰的配置、发布摘要及核验模板约束 |
| B：所有方案都强制逐对象交代，未选择 | 即使只输出筛选清单，也必须声明哪些输入属于业务对象，并提供所有对象的最终去向 | 规则统一；普通筛选、汇总和多来源处理也需要维护对象与结果对应关系 |

两个选项均保留原始快照、处理统计、问题数据、类型检查和来源权限。差别仅在最终业务去向的交代义务，不是是否允许静默丢数据或把未知算作成功。

另一个必须区分的概念：**已经交代所有对象的处理状态，不等于所有对象都获得了有效核验结论。** 例如 80 个有结论、20 个明确未比较，去向交代可以完整，有效核验仍存在缺口；具体统计口径在后续决策中定义。

本题影响：结果输出配置、发布检查、任务结果展示和外部查询接口。配置的具体字段与界面位置在对象身份和分组关系明确后细化，不由本题预先决定。

### D02：核验方案的结果交代采用什么粒度

**状态：已确认，2026-10-10 用户选择 A。**

决定：采用“原始业务明细的最终去向＋核验单元的比较结论”。每条明细交代去向，需要合并核验时通过成员关系关联单元结论；未形成单元的明细也记录原因。不要求每条原始明细单独调用模型，不将同一单元差异重复计入多个成员明细。

当前代码证据：高值耗材模板先汇总数量，再进行识别及比较；通用 Aggregate 已保存组与成员行的关联数据。已有分组和成员关系可以复用，但不等于已具备原始明细的最终去向核对。当前模板的分组字段只是现状，不作为真实业务分组口径已经正确的证明。

定位：`src/backend/base/langflow/business/templates.py:181`、`src/backend/base/langflow/business/runtime.py:186`。

举例，以下合并计量前提已由业务依据确认，仅用于说明结果粒度：

| 原始明细 | 信息 | 后续情况 |
|---|---|---|
| D001 | 某患者同次就诊的同类别耗材，结算数量 1 | 与 D002 属于同一已确认可比较单元 U01 |
| D002 | 同口径耗材，结算数量 1 | 与 D001 汇总为结算数量 2；U01 识别数量为 1 |
| D003 | 缺少目录分类依据 | 无法确认应进入哪个核验单元 |

| 选项 | 具体方式 | 取舍 |
|---|---|---|
| A：明细去向＋单元结论，已选择 | 原始业务明细逐条关联最终去向；需要合并核验时，真实比较结论记录在核验单元上，并关联全部成员。D003 保留未比较／待确认原因 | 能交代形成单元前的问题；需要分别维护明细身份、单元身份及成员关系 |
| B：只以核验单元交代最终结果，未选择 | 最终结果覆盖以已形成的单元为基准；原始明细及未成组问题仍在快照、中间问题数据中查阅，不要求原始业务明细全部具有最终去向记录 | 最终结果较简单；单元覆盖完整不能证明所有原始业务明细都已得到交代 |

已确认 A 的具体含义：

- D001、D002 分别显示“参与 U01”，通过关联查看同一单元结论；U01 的数量差异为 -1。
- 不把这一个 -1 复制成两条独立明细差异后再次相加，也不凭单元数量差异推断到底是哪条收费明细有误。
- D003 即使未能形成核验单元，也在原始业务明细的最终去向中可见。
- 汇总分别显示原始业务明细数与核验单元数。类别、数量、费用的有效结论数还须按各自事项统计，不能混为一个总通过数。
- 这是方案可声明的结果关系；不要求所有业务都有患者、就诊或固定的分组字段。不需要合并的业务可以一条业务对象对应一个核验单元。
- 参考目录行、影像清单行与原始业务明细不同，不能自动合计成业务对象总数；哪些输入承担业务对象角色还需在方案中声明。

具体主数据身份字段、真实计量分组依据、空键和冲突处置仍需后续明确。本题确认两层结果责任，不表示当前模板分组字段已获得专业计量有效性证明。

### D03：读取或外部调用失败时，按什么范围停止处理

**状态：已确认，2026-10-10 用户选择 A。**

决定：按依赖影响范围隔离失败，在能够确认独立性的前提下，不受影响的部分继续处理。依赖不完整数据或缺失证据的结论停止形成；共享来源故障可以阻断整个分支乃至全部任务。此决定不包含自动重试或自动恢复。

此前约束已明确：不完整的范围数据不能被当作完整依据进行汇总核验；分页不能拆开业务核验单元；未知不能补零；本期不建设自动恢复。本题不重新征询这些约束。

本题确认同一任务可以保留局部有效结果；不能确认独立性时，不默认失败只影响单条记录。

代码核查：

- 数据库与 API 读取均经 `DatasetStore.write_batches` 持久化。API 页数或调用次数达到限制且未取完时明确报错，HTTP 请求异常也向外传播。
- 当前写入失败会移除该次未完成的 Parquet 文件，不登记为完整数据集。这并不等于已经实现失败页、已读数量等完整诊断记录。
- 当前 API 节点按上游记录逐个读取时，某一次请求异常会使整个节点失败；`run_task` 捕获图执行异常后将任务标为 failed。当前没有完整的、按业务单元继续执行的隔离契约。
- 模型读取另有把部分响应错误保存到问题分支的行为；读取类与模型类的失败处理尚未统一。

定位：`sources.py:85`、`sources.py:293`、`datasets.py:107`、`connections.py:172`、`runtime.py:230`。

具体场景：结算原始数据已经完整取得，形成 100 个核验单元。单元 U03 的影像查询失败；其余 99 个单元的数据和证据不依赖 U03 的查询。

| 选项 | 具体方式 | 取舍 |
|---|---|---|
| A：按依赖影响范围隔离，已选择 | U03 记录失败或未知原因，停止依赖该证据的结论；其余 99 个独立单元继续。若共享数据源取数不完整，则阻断全部依赖该来源完整性的处理 | 保留不受影响的有效结果；需要明确失败范围和节点／单元的依赖关系 |
| B：必需读取或调用失败即停止整个任务，未选择 | U03 的必要影像读取失败即停止本次任务的后续处理；此前已保存的记录和结果仍保留 | 执行策略更简单，但局部问题也使其他独立单元无法继续 |

已确认 A 的边界：

1. 结算主数据只取到第 7 页、第 8 页失败时，不能声称全部对象已发现，也不能用前 7 页的数量作为完整结算量。依赖完整范围的汇总与比较停止。
2. 单个单元的证据查询失败时，仅在依赖范围明确、其他单元独立的前提下隔离；不能机械地认为“某次 HTTP 失败总是只影响一条记录”。共享目录、连接或系统故障可能影响整个分支乃至全部任务。
3. 受影响明细按 D02 交代问题或未比较原因，已知原因不是有效核验结论；未读到的明细也不能被虚构成已核对对象。
4. 结果页向平台人员及获授权调用方分别展示执行情况、取数完整性、有效结论和未比较／失败／未知数量；不把局部成功显示成全任务核验通过。
5. 模型超时而远端受理状态未知时，保留该请求的未知状态，不自动重复提交。此处是否继续其他独立单元与自动重试是两个问题。

本题只决定失败隔离范围；具体状态枚举、重跑方式、故障分类配置和保留未封存数据的形式留待后续契约细化，不随本题默认确定。

### D04：业务唯一键重复时，完全重复与事实冲突如何处理

**状态：已确认，2026-10-10 用户选择 A。**

决定：已确认同一业务身份且全部原始业务字段一致的重复记录，合并参与后续处理，只计算一次；每次原始出现均保留并关联同一业务明细。同一业务身份但事实不同的记录全部保留为冲突，停止依赖该冲突事实的结论，不任意采信其中一条。不同业务身份的记录不能仅因内容相同而合并。

本题以来源已约定业务唯一键及其适用范围为前提。例如“来源系统＋医院＋结算明细号”才确定一条结算明细；同一个目录编码、患者或订单分组键不能代替明细唯一键。正常的一对多付款、不同医院重复使用本地编号，不属于这里的同一业务身份重复。

当前证据：`runtime.py:151` 的 Union 去重通过数据集 UUID 和来源行号选择一条，没有区分完全重复与同键不同事实；`relational.py:69` 的 Validate 唯一性检查则把同键多行全部放入问题数据。消融报告 C03 已展示任意保留一条可能采信错误事实。

假设以下均来自同一医院、同一来源，并已确认明细号在本次范围内唯一：

| 情况 | 来源返回的数据 | 风险 |
|---|---|---|
| 完全重复 | API 第 1 页和第 2 页都返回 D001，全部原始业务字段相同、数量均为 1 | 相加会把同一明细计为 2 |
| 同键事实冲突 | D002 出现两次，数量分别为 1 和 2 | 单凭返回顺序无法判断哪条有效 |
| 不同业务明细 | D003、D004 的其他字段都相同，但明细号不同 | 不能因为内容相似而合并 |

| 选项 | 具体方式 | 取舍 |
|---|---|---|
| A：完全重复合并参与处理，事实冲突单独保留，已选择 | D001 后续只计一次；全部原始出现记录仍保留并关联同一业务明细。D002 的冲突记录全部可查，停止依赖该冲突事实的结论，不任意选一条 | 可容纳重复投递和分页重叠；需要区分业务身份、原始出现记录及事实一致性 |
| B：同一唯一键出现多次，一律进入问题数据，未选择 | D001 即使字段完全相同也不参与正常核验；D002 同样进入问题数据，停止受影响结论 | 规则更简单，但无事实矛盾的重复投递也会造成核验缺口 |

已确认 A 的边界：

1. “完全一致”默认比较该来源返回的全部原始业务字段，不能只看本次选中的金额或数量。平台生成的行号、取数时间等技术信息不属于业务事实；格式规范化如有需要，应明确配置并保留原始值。
2. 未声明可靠业务身份时，不自动根据名称相近、金额相同或整行相似推断为同一明细。正常历史版本应先约定版本／有效时间的身份范围，不能默认取最新一条。
3. 每次原始出现都保留来源，并交代是否与另一条完全重复；后续业务数量按合并后的明细计算。接收记录数、不同业务明细数与核验单元数分别说明。

### D06：执行环境升级时，是否接受维护窗口与受影响方案重新发布

3. D03：读取或外部调用失败的隔离范围——已确认 A，按依赖影响范围隔离；随后细化任务状态和数据完整性依据。
4. D04：完全重复与同键不同事实的处理策略——已确认 A，完全重复合并参与处理、事实冲突阻断受影响结论；不默认加入自动来源裁决。
5. D05：缺少事后查询能力的模型服务是否允许正式接入——已确认 A，允许按实际能力接入；专业响应契约及真实服务能力继续核实。
6. D06：执行环境升级时的维护窗口、旧任务与受影响方案处置——已确认 A，单一执行构建，排空后升级并重新发布受影响方案。
7. D07：专业模板的实际接入范围与分阶段验收依据——已确认 A，工程、真实接入和业务效果分阶段验收。

后续选择若已由此前约束明确，直接引用依据，不重复征询。实际字段、响应格式等先查代码和已有接口资料；确实缺失时再询问。

## 6. 改造实施方案入口

具体内容已整理至[改造实施方案](./REFACTORING-DESIGN.md)，与本记录的分工如下：本记录保存用户决定及理由，实施方案把这些决定转为节点、页面、数据、接口和验收要求，不把工程推导标成用户另行确认的选择。

- 首先阅读实施方案第 2—4 节：职责边界、节点目录和两种业务的组合示例。
- 配置人员阅读第 5—6 节：每项配置放在哪里，以及结果身份、覆盖和失败如何表达。
- 实现人员阅读第 7—10 节：专业调用、接口与版本、改造顺序和验收。
- 真实接入负责人阅读第 11 节：待补资料、责任方及所阻塞的验收范围。

仅当出现难以逆转、存在真实取舍且未来读者需要理解原因的决定时，另建 ADR；不为每一个配置选择创建 ADR。
