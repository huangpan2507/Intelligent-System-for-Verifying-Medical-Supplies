# D01—D07 改造实现与工程验收

日期：2026-10-10。依据：[已确认的七项决策](./REFACTORING-PLAN.md)、[实施设计](./REFACTORING-DESIGN.md)。

本次完成的是通用平台的工程改造及构造数据验证。真实结算／目录／影像接口接入、正式计量与费用规则、专业识别效果尚未验收。下列事实以当前代码和本次执行记录为依据，不能用模拟通过替代真实业务通过。

继续使用 Langflow 的图调度和后台 Job；删除业务运行器中重复的前驱递归执行。节点多输出端口共享同次执行，重复任务启动仍有持久认领保护。未新增另一套调度引擎、微服务、专用髋膝分类核心或独立“去重节点”。现有组件类名保持不变。

## 2. 如何在页面使用

1. **连接管理 `/business/connections`**：登记 MySQL、PostgreSQL、API 或模型连接。数据库节点选择连接和表；API 节点选择连接、路径及响应字段。API 与数据库是两个节点类型，可以出现在同一个流程内。鉴权头名称／前缀可配置，密钥仍单独保存。
2. **画布中的 Validate**：配置身份名称、来源命名空间与业务键。只做一般数据校验时可以不声明身份。配置“业务键”并不等于随意按该字段取第一条。
3. **画布中的 API**：声明完整性范围和依据。逐业务对象请求且完整性范围独立时，选择 `object`；覆盖整个查询范围时用 `range`。完整性声明须有上游契约或响应依据，不是绕过检查的开关。
4. **画布中的主 Output**：展开“结果交代约定”，核验模式选择原始读取节点、已有的 Validate 身份、每个事项的单元节点与结果端口，并声明范围外／未比较等去向。节点与字段可以下拉选择，不需要在发布页再写一份业务条件。
5. **业务方案 `/business`**：发布版本显示只读的来源、条件及结果责任摘要。发布后启用版本供新任务使用。维护区显示是否受理新任务和待排空任务数；历史版本提供“按此版本配置重新校验发布”。
6. **任务详情 `/business/tasks/{id}`**：分别看执行状态、已收到记录的去向、来源完整性和各事项的单元结论。点击 `category`、`quantity`、`fee` 查看对应数据集；“查看数据集”可切换原始快照、问题、重复关系和成员来源；展开“模型与专业服务请求记录”查看输入、响应及状态。

“执行完成”“记录已交代”“有有效比较结论”“来源已完整取得”是不同判断。记录未比较但原因明确，可以属于已交代；没有声明或无法证明的来源完整性不会被自动算作 100%。旧 `unresolved_rows` 保持按节点累计的兼容含义，不用它作为业务覆盖分母。

公共查询和页面使用相同的 `assessment`，不会各自计算一套结论。请求列表与详情位于 `/api/v1/business/tasks/{id}/requests` 和 `/{request_id}`，继续校验任务所属来源；外部来源不能查看其他来源的请求、响应或数据集。

## 3. 高值耗材模板具体改变

```text
结算读取 → 身份校验 → 医保／耗材事实分流 → 目录关联 → 目标类别分流
    → 目标数据校验 → 按业务单元汇总
    → 检查查询 → 归属检查 → 序列查询 → 影像清单 → 证据关联
    → 专业观察 → 观察合法性检查
        ├→ 类别比较
        ├→ 数量前提检查 → 数量比较
        └→ 费用前提检查 → 费用比较
    → 各结果与问题输出 → 公共最终去向核对
```

模板仍可以出现多个同类型节点。侧栏的 14 种通用能力加可选 Imaging 是能力目录，不是每个业务必须经历的固定 15 步。

- 结算期待数量不发送给专业识别模拟端，避免“把答案传给模型再拿回来比较”。模拟响应由证据／对象夹具独立给出，包含正例与负例。
- 专业适配负责请求与响应映射，普通的非负、证据存在、单位、类别和范围前提由模板的 Validate／Filter 表达。
- 类别可判断不代表数量可比较；数量可比较不代表费用可比较。各事项分别声明前提与未比较原因。
- 示例费用仅在构造数据的单位、对象、范围和统一单价等前提满足时折算；不同单价无法归属时费用未比较，不猜平均价。
- 默认 `baseline` 提供 6 次结算原始出现；模拟专用 `adversarial` 提供 18 次出现、15 个非空业务身份及 1 次缺身份出现，包含完全重复、冲突、无影像、非法数量、未知分类／事实、明确范围外和混合价格。
- 模板没有要求管理员在发布页面穷举耗材编码。分类依据由目录读取与关联取得，目标类别是筛选配置；目录没有相应依据时保留未知。

专业模拟使用构造的影像引用并显式带 `simulated=true`。没有进行真实 DICOM 下载、解码、跨视图实体识别或医学效果测量。

消融不是单纯再跑一次成功示例。以下对照在同一测试中保留相同输入、移除指定保护，再断言可观察的错误：

| 机制 | 保留时 | 移除或替代时 |
|---|---|---|
| 原始事实身份校验 | 7 次出现中，2 条可用事实、1 条重复关系、4 条冲突／缺身份问题；投影掉原始差异字段仍能识别冲突 | 只用普通空配置 Validate，7 条全部进入可用数据 |
| 最终结果责任核对 | 应交代 A、B，只连通 A 的结果时，明确显示 B 未比较和 1 个覆盖缺口 | 去掉责任声明，相同输出只得到普通处理状态，不能发现遗漏 |
| 问题成员依赖阻断 | A 组的无效成员使 A 未比较，独立 B 组仍相同 | 去掉阻断标识，A 的局部有效合计被错误判为相同 |
| 数量比较前提 | 专业负数量不会形成数量结论，同时保留其他正例的相同／不同结果 | 绕开数量前提、保持相同观察响应，负数量被比较器判成业务差异 |
| 请求登记边界 | 测试在实际发送函数中查询到已提交的登记；登记写入失败时发送次数为零；超时只发送一次，远端未知 | 注入登记失败验证不能越过边界；不通过自动重发制造“成功” |
| 删除冗余递归调度 | 原生 Graph、子流程、分支、多端口测试仍正确；节点多端口没有重复执行 | 没有保留第二套调度作为必要机制；旧审查记录保留其原始实验范围 |

另覆盖共享 API 分页失败保留前批、独立对象 API 失败继续、精度与溢出不静默舍入、HTTP 202／非法 JSON／部分合法输出的不同状态、维护幂等、来源隔离等反例。强制字段缺失的问题行使用可空的问题端口结构，避免“保存错误记录时再次因缺少该字段而失败”。

补充发现并修复了 API 类型转换导致收到的整批原始记录未落盘的问题：例如金额为 `invalid` 时仍保存每次出现的 `_raw_record`／`_raw_facts`，问题端口保存 `_raw_response`，该请求范围标记为不完整。被拒绝批次的规范化字段可以为空，不能据此推断原始字段本来为空；原始值从原始记录字段查看。独立对象的其他请求仍可继续。修复前的失败断言和修复后结果一并留档。

本轮证据位于 [`evidence/refactoring-20261010/`](./evidence/refactoring-20261010/)。原 [`spikes/001-business-architecture-ablation/`](../../spikes/001-business-architecture-ablation/) 的实验没有改写成新结果。

浏览器使用真实本地业务服务。仅外部模板商店的标签请求固定为空列表，以隔离本机访问该外部商店时的证书错误，不据此宣称外部商店联通。验证图片：[结果与请求](./evidence/refactoring-20261010/results-and-requests.png)、[画布结果责任配置](./evidence/refactoring-20261010/canvas-obligation.png)。复现入口是 `scripts/business/verify_browser.py`，可用 `--task` 复用已保存的模拟反例任务。

## 6. 版本与历史

- 新内置方案编码：`demo.cross_database.v2`、`demo.consumables.v2`。原两个无 `.v2` 的内置示例停用新任务受理，原画布、版本、结果保留。未自动修改用户自建方案。
- 本次部署增量创建请求、评估表和维护状态；不重建旧任务表、不改写旧状态。
- 旧 Union 任意去重、旧 Imaging 将比较门槛藏在调用器中的配置不能直接假装兼容；发布器明确报错，按新版节点配置迁移。
- 受理固定实际版本；执行构建不兼容时拒绝新任务并要求明确重发版，不拿最新草稿执行旧任务。
- 受理维护状态控制所有通用方案。升级前应先停受理、排空，再替换运行环境；不承诺在旧进程已经丢失后自动恢复其精确运行环境。

一键启动／重启命令，在仓库根目录和已配置的本地环境运行：

```bash
bash scripts/business/start_local.sh --restart
```

本次该命令已在受控工具会话内完成重启、维护排空检查和 v5 发布；通过保留运行会话完成浏览器联调。尝试转为宿主后台持久启动时，自动审批服务因网络连接中断未通过，未执行该宿主操作。需要独立于工具会话长期运行时，在自己的 WSL 终端执行上述命令；脚本由 tmux 保持服务。

## 7. 尚未验收的实际能力边界

1. 真实结算、目录分类、检查／序列／影像服务的地址、鉴权、分页、完整性及字段含义，需要服务方实际契约。已有三段影像接口资料可用于配置映射，但模拟三段查询不等于该真实接口已接通。
2. 真实患者／就诊／时间／部位／侧别关联依据、计量单位与覆盖范围、退费冲正和费用分摊规则，需要业务责任方确认。不能把示例的统一单价规则当正式政策。
3. 模型独立请求台账和同步协议已实现；当前没有供应方专用的异步查询／恢复适配。HTTP 202 或超时保留未完成／未知，不自动轮询未声明的地址、不自动补提。
4. 请求业务输入和响应目前按单次请求保存在台账 JSON；传递的是配置字段及证据引用，不是 DICOM 文件字节。海量证据／响应的外部工件分存和真实供应方处理清单对账仍需按实际协议实现、测量。
5. 独立失败隔离依赖明确的对象范围和可追溯的业务键。不能定位影响范围时采取保守阻断，不声称能够推断任意业务的正确故障边界。
6. 未开展专业模型训练、医学准确率评估、多租户生产负载、分布式执行或中断任务自动续跑。本轮遵循单部署范围。

上述真实事实缺口的责任方和阻塞范围继续见[实施设计第 11 节](./REFACTORING-DESIGN.md#11-真实接入资料责任方与阻塞范围)。
