## 1. 结论与已核实事实

当前问题同时存在于呈现层和配置维护方式：一些必要的概念被平铺成相互独立的表单，重叠信息需要多次选择；嵌套列表放大了编辑高度。不能只通过减小字体、隐藏必要判断或删除校验来精简。

| 问题 | 当前事实 | 设计方向及确认状态 |
|---|---|---|
| Input fields 与 Evidence fields 重叠 | 模型输入有 5 列，允许引用的依据有 3 列；后者必须属于前者 | Q25 已同意：同一字段表标记用途，消除重复选择，保留语义区别 |
| 三处类别配置平铺 | categories 是明确类别，target_categories 是继续处理的子集，unknown_category 是无法确定时使用的标签 | Q26 已同意：类别与去向在一处维护；无法确定以单独状态说明呈现 |
| 每条规则重复选择字段 | 当前 3 条规则使用相同的 3 个字段、顺序也相同 | Q27/Q28 已同意：公共字段自动来自分类依据字段，紧凑规则行继承，必要时逐条覆盖 |
| 提示词重复写类别和字段名单 | 当前 Prompt 另行写死四种结果、三个可引用字段；执行时没有按配置自动同步这些名单 | Q29 已同意：按字段用途与类别配置生成结构性约束，业务判断说明另行维护 |
| 配置层级混杂 | 字段、分类目标、规则、模型连接、协议路径和调用上限并列 | 按业务操作组织页面，协议和调用限制进入明确的高级区域 |

代码依据：

- [catalog.py](../../src/backend/base/langflow/business/catalog.py)：12 项配置的结构；规则类别当前是文本输入，并非类别列表联动选择。
- [classification.py](../../src/backend/base/langflow/business/classification.py)：依据字段是输入字段子集、规则字段是依据字段子集、继续处理类别是明确类别子集；未知标签不能与明确类别重复。
- [SchemaForm.tsx](../../src/frontend/src/pages/BusinessPage/SchemaForm.tsx)：数组元素逐项生成带边框、内边距、删除按钮的卡片；规则数组内还有字段数组，因此形成截图中的多层纵向表单。
- [core_classification.py](../../scripts/business/core_classification.py)：当前业务 Prompt 中单独维护类别和证据字段文字。
- [sources.py](../../src/backend/base/langflow/business/sources.py)：模型调用只附加输出字段契约，未自动将分类配置的类别与证据字段名单编入 Prompt。

## 2. 五个模型输入与三个引用依据

两者并非相同职责。手术名称、规格可以提供背景，但当前采纳分类时还需要具体耗材描述支持。字段允许作为依据，不代表该字段任意一个值都足以证明分类。

例如两条明细的手术名称同为“人工全髋关节置换术”，一条商品名为“人工髋关节假体”，另一条为“医用缝线（模拟对照项）”。模型可以看相同的手术背景，但不能仅凭背景将两条都归为人工髋关节。规格若只有“一套”，也不能独立确定髋／膝类别。

Q25 已确认将配置改成一张“分类字段”表：

| 字段 | 用途（已确认） |
|---|---|
| PRODNAME | 分类依据 |
| HOS_PROJ_NAME | 分类依据 |
| MEDINS_LIST_NAME | 分类依据 |
| HILIST_NAME | 辅助上下文 |
| SPEC | 辅助上下文 |

两种用途的字段都发送给模型；只有“分类依据”字段可被引用为当前契约中的那一段依据原文。沿用一次返回一个引用字段和一段原文的契约，不由本次布局讨论自动扩展为多段引用。

这是当前髋膝模板已确认的字段用途，不是通用节点对特定数据库列名的硬编码。其他来源如果在规格中明确记录产品类别，可以按其实际含义重新定义用途，不能仅凭列名自动决定。相关业务术语已写入 [GLOSSARY.md](../../GLOSSARY.md)，不把布局和保存格式写入词汇定义。

## 3. 类别与处理去向

Q26 已确认用一张表配置已明确的类别及其后续处理方式：

| 类别 | 处理方式 |
|---|---|
| 人工髋关节 | 继续处理 |
| 人工膝关节 | 继续处理 |
| 其他 | 不进入后续核验 |

下方固定说明：“无法确定：尚不能确认类别，保留到问题结果，不进入后续核验。”

“其他”表示有依据地确定不属于目标类别；“无法确定”表示尚不能形成分类结论。未知不是普通类别表中任意填写、任意路由的一项。没有规则命中先进入模型辅助，仍不能确定时保留未知，不直接落入其他。

规则的输出类别从同一类别表选择，不再手填第二份名称。用户已同意取消未知标签编辑，同时兼容旧流程：当前 unknown_category 并非纯显示文字，它参与输出和分流，不能只从 UI 删除而不提供执行配置。新配置使用系统的无法确定标签，旧配置的已保存语义仍须保留，不改写历史结果。

## 4. 紧凑规则编辑

Q27/Q28 已确认的紧凑布局示意：

> 下表已按 Q30 修订为两条业务规则，并按 Q31 显式选用新增关键词模式。“等于非关节耗材（模拟对照项）→其他”仅保留为测试夹具中的规则，不再作为业务模板建议，见第 8 节。当前运行配置尚未按这项设计更新。

```text
公共匹配字段（自动取自分类依据；任一字段满足即可）
[PRODNAME] [HOS_PROJ_NAME] [MEDINS_LIST_NAME]  [前往分类字段修改]

范围           比较方式           关键词                 输出类别       操作
公共字段       包含全部关键词     [人工] [髋关节]        人工髋关节     删除
公共字段       包含全部关键词     [人工] [膝关节]        人工膝关节     删除
+ 添加规则
```

每条默认显示“公共字段”；确需不同范围时展开该条字段设置，并显示“自定义字段”及字段摘要。公共字段为只读摘要，新增、移除或修改用途统一在分类字段表进行；单条自定义范围使用紧凑多选。不重复显示为每条内部的三张卡片，不让每个字段单独占一行删除按钮。

字段来源在区域顶部说明为 SettlementChecks.Valid，选择器保留完整字段名、类型、搜索及可访问的详细信息；不能为压缩布局而让使用者无法辨认字段来源。宽编辑区使用表格；窄侧栏采用每条两行的紧凑布局，必要时可扩展编辑区域，不强行压入多列表格或缩小字号。

保留现有判断语义：

- 同一规则内任一字段匹配即可；contains 为文字包含，eq 为全文相等。
- 不同类别同时命中不能变成“第一条优先”，仍视为冲突。
- 同一类别多处命中，当前规则和字段顺序决定代表性引用；迁移需保留有效顺序。
- 单条字段覆盖不能被公共字段静默替换；修改公共字段只影响继承它的规则。
- 仅相同的有序字段列表可以无损提取为公共字段。已有不同字段集合的规则保留覆盖。

当前规则字段需要属于证据字段。Q28 已同意让公共字段自动取自全部“分类依据”字段，只在单条例外时选择子集，免于再维护一份相同名单。修改字段用途时，应显示受影响规则，不静默删除自定义引用；自定义规则失去所引用的依据字段时必须明确修正，不能保存为含失效引用的有效规则。

## 5. 页面组织与实施约束

不另建泛化规则平台。仍沿用通用 Classification 能力与髋膝模板配置，保留继续处理、明确排除、无法确定三种业务去向及源记录追溯。Q33 将对外输出简化为 Data、Issues 两口，后两种去向在 Issues 内按记录区分，详见第 10 节。

页面按已确认配置关系组织为“分类字段 → 类别与去向 → 分类规则 → 模型辅助”，各部分只维护其负责的事实。连接和模型名称应可见；协议路径、调用上限和冲突条件等按作用分组展开，不因折叠而删除校验。

Q29 已同意采用“系统生成结构性约束＋可编辑业务说明”：字段用途、类别、引用和 JSON 输出格式跟随配置生成，完整发送内容可展开查看；用户只编辑业务判断说明。原文校验和其他运行时约束仍由程序执行，不能用提示词代替。旧 Prompt 是完整指令，不能未经检查直接当成纯业务说明拼接，需要避免保留失效名单。

删除、改名或改用途后，应检查规则引用和下游 Studies/Compare 中的类别配置；失效引用明确提示，不能默默猜测替换。当前冲突检查可以引用未发送模型的上游字段，不能在合并字段表时无意取消该能力。

兼容必须保持有效配置而非只保持页面外观：旧输入／依据名单需还原用途；原本不同的规则字段子集需保留为自定义范围；保留规则和引用字段顺序。当前后端仍要求每条规则包含 fields，未知标签也为必需配置；实施应提供一致的配置转换或协议升级，不能直接把新 UI 对象交给旧执行器。公共字段继承关系在保存、刷新后需仍然成立，不能重新打开后变成三份独立名单。

新配置使用系统默认的无法确定标签；旧自定义标签保留其原有分流与结果语义，可作为兼容信息只读展示。原 42 节点方案、未迁移配置和旧发布任务不因新编辑器被覆盖。结构性约束生成与旧完整 Prompt 的迁移需分别验证，不将所有历史提示词自动解释为纯业务说明。

仅调整页面不应改变规则优先、模型自报置信度仅供展示、已确认冲突结果不得自动通过等既有语义。Q31/Q32 是后续明确同意的匹配和调用路径扩展，应单独实现、验证，不能混称为纯布局调整。是否避免向模型发送已确定存在冲突的行，不由本轮布局修改自动引入。

## 7. 确认并实施后的验收目标

以下为待实施的验收目标，不是本轮测试通过声明：

1. 五个字段各配置一次，当前三项依据／两项上下文的有效输入与引用限制保持一致；公共匹配字段自动取自三项依据，无需再次勾选。
2. 类别只维护一次，规则输出只能引用已声明类别；未知与其他保持不同去向。
3. 业务规则的公共字段只显示一次；新增、删除、修改与自定义字段覆盖均可操作；保存并重新打开后仍保持继承／自定义区别。
4. 既有相同匹配配置执行前后，规则分类、模型待处理行、源数量／单价、分类结果与三种业务去向行数一致；按 Q33 对外合并后，Issues 总行数应等于原 Excluded 与 Issues 行数之和。
5. 字段或类别调整时，结构性模型约束同步；失效的规则／下游引用明确提示，不静默生成新列或猜测类别。
6. 能从旧配置恢复等价界面；不改写旧发布版本及历史任务，不将未确认的旧标签丢失。
7. 在现有窄侧栏和较宽编辑区域均能读清完整条件、使用键盘操作；压缩层级不以缩小字号或隐藏关键条件实现。
8. 按 Q30 移除业务模板中的模拟“其他”规则后，测试夹具仍可验证明确其他的规则分流；业务模板不靠特殊测试字眼识别其他。对该删除的行为变化单独验收，不能宣称所有旧输入都与删除前等价。当前两条髋／膝核心样例不依赖该模拟规则。
9. 新增模式验证同一字段内全部词组同时出现、词序不限制、不跨字段拼凑；关键词列表不能为空，不能含空词组，避免空条件匹配所有记录。旧 contains/eq 行为不变，不能让新增操作落入旧实现的相等比较分支。
10. 配置“未使用”“取出器”等提示时，命中原文出现这些词应交模型，不直接定类或排除；疑似歧义不错误触发硬性冲突阻断，真正的既有冲突不能因走模型而被覆盖。
11. 模型引用仍须为允许字段中实际存在的连续原文，不能改为全部关键词、子序列或相似引用；保留新模式的条件、命中字段和实际原文以便复核。
12. 只连接 Data 的分类节点在另两类结果非空时也能执行并保存去向。合并后的 Issues 分别显示排除与未确定；排除不增加错误或待处理，最终按行统计去向，不把同一记录同时标成排除和未比较。
13. 旧 Excluded/Issues 消费者、节点内嵌源码与 Results 引用同步迁移；核心 10 节点画布不为合并额外添加分流节点。旧任务可查看、旧发布包不改写；再次执行采用经过预检的新兼容版本。

## 8. 手术名称样例的实际路径与模拟规则复核

用户提供的截图列名为 hilist_name，红框内三个值依次为：

1. 人工全髋关节置换术
2. 人工全髋关节再置加收
3. 髋关节表面置换术

需要分开检查字段范围和文字匹配两件事：

- 当前正常髋／膝匹配规则检查 PRODNAME、HOS_PROJ_NAME、MEDINS_LIST_NAME，不检查 HILIST_NAME。后者用于上下文及已配置的髋／膝冲突核对。
- 当前 contains 是连续文字包含，不会去掉“全”、自动推断同义词或理解手术含义。前两个字符串含“人工全髋关节”，并不含连续子串“人工髋关节”；第三个也不含这个子串。当前膝规则同样不会命中。
- 文档中“人工髋／膝关节”是对两条独立规则的概括，不是把含斜杠的整段文字作为匹配值。

### 不同输入情况对应的结果

以下讨论以记录已进入 Classification、其余字段无类别冲突为前提；不是对截图之外未提供的数据作假设。

| HILIST_NAME | 三个耗材字段的情况 | 预模型规则结果 | 正常后续路径 |
|---|---|---|---|
| 上述任一名称 | 均无明确规则命中，例如只有“材料名称待补充” | 无法确定 | 交模型辅助 |
| 上述任一名称 | 任一字段为“人工髋关节（某型号）” | 人工髋关节 | 使用规则结果 |
| 上述任一名称 | 耗材字段也只是原样重复该手术名称 | 当前文字规则不命中 | 交模型辅助；不能据此保证最终判为人工髋关节 |

因此，不能仅凭截图的一列断言完整记录一定走哪一路；如果不存在其他耗材字段的明确命中，三条都进入模型辅助阶段。进入模型不等于模型结论已被采用。

本轮已用当前 `classification.rule_query` 在内存 DuckDB 中验证上述组合：现有完整流程模板与已保存 10 节点 graph 各执行同样的 34 条局部输入，路由相关配置与结果一致。覆盖三种名称、耗材字段为空、单个／多个字段命中、材料字段重复手术文字，以及模拟其他的精确命中和冲突。这里只验证规则阶段及是否进入模型输入集，不发起模型请求，不将局部构造行冒充实际来源样本或新业务任务。

模型会同时看到手术名称和已选耗材信息。若可引用耗材信息为空，当前证据校验不能接受只有手术名称的目标类别结论；信息不足时最终仍为无法确定，而不是自动归为其他。若耗材字段只是重复手术文字，也不能仅凭“原文引用存在”证明它在语义上充分支持耗材类别；模型还需遵循对应业务说明。

不能简单把 contains 的比较值放宽为“髋关节”：这样截图中“髋关节脱位切开复位术”等其他名称也会文字命中，偏离“依据该行具体耗材信息分类”的已确认口径。本轮不把手术名称清单自动加入耗材白名单，也不修改用户已确认属于耗材的 CNT/PRIC 含义。

### “非关节耗材（模拟对照项）”不是现实名称规则

这条等值条件只对测试构造的字面值起作用。真实名称不需要包含“非关节耗材”几个字才能归为其他；真实类别应依据原始描述形成，而不能预先把希望得到的结论写进源名称来代替识别。

此前将该规则继续列在面向业务使用者的配置示例里不恰当。Q30 已确认：从业务模板的正常配置中移除，测试夹具可以保留；类别表仍保留“其他”，让没有命中明确规则的记录由模型结合具体耗材信息判断为目标、其他或无法确定。不能改成“未命中髋／膝规则则为其他”。

Q30 已收到明确同意。本文的业务规则示意已删除该条；本轮仍只修订设计说明，现有模板文件、保存画布与发布版本尚未实施此项变更，也未发起在线模型请求。

## 9. 插入文字、词组组合与规则覆盖范围

用户提出：不能因为“人工全髋关节”多了“全”就只能调用模型，希望文字不连续也可以命中。这可以增加为规则能力；当前 Classification 的 op 只有 contains/eq，尚不支持下列新增模式。现有 contains 本身为“包含连续片段”，并非要求整个字段与比较值全文相等。

### 候选匹配方式

| 方式 | 对“人工髋关节”的解释 | “人工全髋关节置换术”的文字匹配 | 边界 |
|---|---|---|---|
| 当前连续包含 | 寻找完整连续片段“人工髋关节” | 不命中 | 简单明确，但不覆盖插字变体 |
| 逐字有序包含 | 人、工、髋、关、节按顺序出现，可间隔其他文字 | 命中 | 单字可能分散在不同词中；不能据此确认词义关联 |
| 同一字段包含全部词组（Q31 推荐） | 在同一字段找到完整词组“人工”和“髋关节”，不限制词组顺序 | 命中 | 保留词组，不跨列拼凑；共现仍不等于业务含义成立 |
| 明确名称变体列表 | 匹配事先确认的“人工髋关节”或“人工全髋关节”等片段 | 命中 | 范围更明确，但需维护已知变体，片段包含仍不解释上下文 |

Q31 已确认新增“同一字段包含全部关键词”，原有连续包含和全文相等保持原义。关键词用可见词组配置，不自动按单字拆分，不把现有 contains 静默改成宽松方式，也不要求业务使用者编写正则表达式。

单字段判断后，再按规则原有方式对多个依据字段取“任一字段满足”。例如 PRODNAME 只有“人工”，HOS_PROJ_NAME 只有“髋关节”，两个字段不能拼在一起命中。保存规则中应明确匹配模式、词组及所引用字段，结果应保留实际命中原文。

### 字符匹配与业务判断仍是两件事

以下仅是定义匹配语义的构造文本，不是对真实表内容或临床类别的断言：

- “人工髋部支具与膝关节配件”可能凑齐人、工、髋、关、节的顺序，却没有连续词组“髋关节”；逐字方式过于宽泛。
- “未使用人工全髋关节”同时包含“人工”和“髋关节”，但文字含有否定，不能仅据词组共现采纳目标类别。
- “人工髋关节取出器”包含现有连续片段，也包含两个词组；现有 contains 同样不能独立区分被描述对象和相关器械，不能把这个局限只归咎于新增匹配模式。
- “髋关节表面置换术”没有“人工”，因此人工＋髋关节仍不命中；不能声称一个词组条件解决全部别名或语义理解。

Q32 已确认：规则匹配成功后，若命中原文还包含已配置的歧义提示词，则交给模型进一步判断；正常命中且无提示、无已知冲突时采用规则结果。提示词在可展开配置中明确列出，例如“未使用”“取出器”，不声称有限词表能识别全部语义歧义，也不把提示词命中直接判为其他或排除。业务含义见 [词汇表的分类歧义提示](../../GLOSSARY.md)。

检查对象是实际匹配了分类规则的依据字段原文；不能从不同字段拼凑一次词组命中。存在多个规则命中字段时，不能因为展示时只选了第一段证据就跳过其他命中字段中的提示。疑似歧义只取消这次规则自动定类，并保留触发字段、原文与提示词供查看，模型仍按原文依据要求作判断。已确认事实冲突仍保持原有处理；不能沿用原 `_classification_conflict` 的硬性阻断语义来标记“需要模型进一步判断”，否则模型结论永远无法被采用。

这项歧义检查不限定只用于新增全部关键词模式：当前连续 contains 对“非人工髋关节”“人工髋关节取出器”也会文字命中，任何配置了同样提示的规则都应按同一约定处理。具体提示词是业务配置，不在通用节点中固定医疗字词。只维护一份公共提示配置，不将同样词表重复展开到每条规则。

本轮讨论只调整匹配方式，沿用 Q25 的字段用途：三个耗材字段作为分类依据，HILIST_NAME/SPEC 作为辅助上下文。即使新算法能在截图的手术名称中匹配词组，也不会自动将仅有 HILIST_NAME 的命中变成耗材分类结论。若用户后续要改变手术字段职责，应单独确认业务依据，而不是通过放宽字符串匹配隐式改变。

能减少多少模型调用，需要在有预期分类结果的名称样本上同时统计规则覆盖率、误分类与模型调用比例。当前两条核心样例不能证明真实数据绝大多数会走模型，也不能保证扩大文字匹配后大部分都能正确走规则。

已完成无网络的局部语义实验：以 10 段构造文本比较连续包含、逐字有序包含、全部关键词和明确变体四种方式，确认全部关键词覆盖“人工全髋关节”，也会匹配上述否定／器械等反例；逐字方式还会匹配“人工髋部支具与膝关节配件”。另通过当前执行器验证了现有 contains 的实际规则行为。这是局部原型与现有实现对照，不代表新增运算符已经接入 UI、发布或正式运行。

补充通过现有受限表达式与 DuckDB 验证了五项断言：单字段“人工全髋关节置换术”命中；词序反转的“髋关节用人工材料”命中；两个词组分别在两列中不命中；“人工髋部支具与膝关节配件”不命中；三字段均为空不命中。正确组合是字段内部 AND、字段之间 OR；将“人工”和“髋关节”拆成两条独立规则会变成 OR，不满足本约定。

### 最终处理示意与兼容边界

```text
在同一个依据字段中检查全部关键词
├─ 没有命中 → 模型辅助
└─ 命中
   ├─ 已确认冲突 → 按既有冲突要求保留无法确定
   ├─ 命中已配置歧义提示 → 模型辅助，按原文依据要求检查结果
   └─ 无提示、无已知冲突 → 采用规则分类
```

上图描述分类结果的采用条件。现有硬性冲突行仍可能被发送模型，但模型结果不会覆盖其冲突；避免这类调用不在本次已确认变更中。提示词未覆盖的语义问题仍可能存在，需要样例复核，不能把“没有命中提示词”解释为所有歧义均已排除。

模型的依据引用校验仍保持“源字段中存在这段连续原文”，不能随分类规则放宽为关键词共现或逐字子序列。新操作仅影响明确选用它的规则。实施时髋膝模板显式选择“包含全部关键词”；历史 contains 规则、旧发布版本及历史结果不被静默改义。

Q31/Q32 均已确认，尚未执行新增算法的业务任务，也未调用在线模型。

## 10. 输出口连线、业务价值与 Q33 两口方案

### 当前实现：只连接 Data 不会因其他输出未连接而报错

| 当前端口 | 含义 | 核心流程的接法 | 需要专门处理时 |
|---|---|---|---|
| Data | 已确定属于继续核验的目标类别 | 连 Studies 的 Data 输入 | 继续检查关联、序列关联、影像与比较 |
| Excluded | 已确定属于非目标类别 | 不连线 | 可接 Output 展示排除清单，或其他专门分支 |
| Issues | 无法确定类别或分类结论不能被接受 | 不连线 | 可接 Filter 按原因分流，或 Output 查看未确定清单 |

没有每个输出口必须被消费的要求。编译器验证实际连线是否合法、下游必需输入是否齐全；不因 Classification 的 Excluded/Issues 没有出边而报错。若另放了一个需要输入的下游节点却没有连接它，那是缺少必需输入，与源节点闲置输出不是同一问题。完整发布流程仍需要 Output。

不应将三口全部接进 Studies：它需要继续核验的目标记录，当前 Data 输入也只接受一个数据集。非目标记录与未确定记录并不因需要保存就必须继续查询影像。

Classification 被执行时会生成并保存三个数据集，运行器保存输出引用，任务详情可查看；是否画出下游连线不决定这些结果是否保存。代码依据：[compiler.py](../../src/backend/base/langflow/business/compiler.py)、[classification.py](../../src/backend/base/langflow/business/classification.py)、[runtime.py](../../src/backend/base/langflow/business/runtime.py)、[datasets.py](../../src/backend/base/langflow/business/datasets.py)。

已保存的核心图只有 `Classification.Data → Studies.Data` 一条分类节点出边。验收任务 `c07d6d7a-8419-42aa-8731-9fd76ceaeb47` 状态 completed，Classification 为 Data 2／Excluded 0／Issues 0，Studies 与 Results 均为 2，任务去向核算 accounted、覆盖缺口 0。该证据证明未连接端口允许存在；两条侧支非空时仍保存的结论来自代码检查，不能把这次空侧支任务称为非空侧支端到端验收。

### 没有连线，不代表未参与去向核算

本核心模板 Results 已在 obligation.dispositions 中直接引用：

- Classification.excluded → excluded / other_material。
- Classification.issues → uncompared / undetermined_category。

这些引用从节点已保存输出读取，不需要再画两条线。**结果保存与最终报告中的去向核算是两件事**：任意新画布若没有相应结果约定，不应承诺只要保存就会自动完成该业务的核算。这里是当前核心模板已配好，Q33 实施时需要同步维护。

### 排除状态有价值，独立端口并非业务必需

假设进入分类的是 100 条有效医保耗材明细，其中 60 条目标、30 条明确其他、10 条无法确定：后续核验 60 条，排除 30 条，待进一步判断 10 条。若把后 40 条都看成错误，就错误增加待处理；若直接丢掉，则无法解释收到 100 条为何只核验 60 条。本例用于说明统计口径，不是实际任务行数。

“明确排除”记录的是分类及其与本次核验范围的关系，不表示源记录错误、收费有误或没有业务价值。它可以与未确定记录共用物理出口，只要状态和依据保留。

### Q33 已确认：Data、Issues 两个输出

```text
Classification
├─ Data：继续核验 ──→ Studies
└─ Issues：未进入后续核验（可以不连线）
   ├─ 已排除：非目标类别，不计为错误或待处理
   └─ 无法确定：待进一步处理，保留未确定原因
```

合并后保留原始字段、类别、分类方式、原因、引用及来源追溯；明确增加或提供可机器读取的逐条去向标记，不能只靠页面颜色或端口名区分。任务页分别展示和统计两类记录，Issues 总量不再等于待处理数量。是否自动安排人工复核或再次调用服务不在本项决定内。

只接 Data 的核心画布仍为 10 节点，Issues 无须接额外节点才能保存、查看及纳入已配置的去向核算。以后业务确实需要区分处理两类记录，再通过已有 Filter 按状态分流。

### 实施必须同步的内容

1. 端口定义、分类数据集和节点输出结构：真实合并 Excluded 与 Issues，保留两类状态，不只是隐藏一个连线口。
2. 待处理统计：[api.py](../../src/backend/base/langflow/business/api.py) 当前按 issues/unknown 的 blocking_rows 累加，没有时用整个数据集行数。合并后必须只把需处理记录计入相应数量，排除行不增加待处理；中间模型数据也不能因合并造成新的重复计算。
3. 去向核算：当前 [catalog.py](../../src/backend/base/langflow/business/catalog.py) 和 [coverage.py](../../src/backend/base/langflow/business/coverage.py) 将一个引用数据集整体赋为固定 status/reason。需要支持按记录区分，或等价的内部分类核算，不能把同一混合口同时声明为全口 excluded 与全口 uncompared。
4. 迁移：旧连线若确实消费 Excluded/Issues，须保留各自原本的数据范围；当前核心图只有 Data 出边，可直接保持主连线。Results 中旧 Excluded 引用必须迁移，否则删除端口会导致发布预检报未知引用。
5. 兼容：当前画布内嵌组件源码有一致性检查，发布包有运行版本校验，需同步刷新、预检和重新发布；不能只删 Python 输出定义就宣布完成。旧发布包、历史任务不就地改写。

本轮 Q33 已确认并记录在 ADR，代码、现有画布与发布版本仍保持三口，尚未执行两口实现及验收。
