# 监管流程入口：任务入参与参数定义的职责复核

日期：2026-10-13。

状态：用户已确认 Q13—Q15 并明确要求实现代码。任务入口、固定输入约定、公共 API 最小检查、监管编号保存和按任务只读查看已实现，通过本地真实 Worker、数据库查询及浏览器验收。前面的“当前实现”表记录改造前事实；最新实现及检查结果见文末。

## 讨论起点

用户指出：监管端已经选择医院、起止日期、规则并发起请求，智能体端的入口应展示本次收到的条件，不应要求在每张画布里重新配置参数定义、必填、默认值和枚举。提供的时序图还包含后端监管编号。

该意见涉及入口职责，不只是 Enum、Description 的位置调整。此前把通用参数编辑器解释为本业务的最终入口界面不够准确。改造前的实现不会因为接入真实监管端而自动切换成只读展示，因此本轮新增了专用任务入口。

本轮沿用医院名称、同一组任务起止时间、单个规则对应所执行流程的描述，不重新引入逐结算向前推七天的时间窗。结算和检查读取不同表中的实际时间字段，但使用同一组任务边界。

改造前该画布声明 hospital_name、start、end，均为 string、required=true，并带有模拟默认值。未设置 Enum。因而当时这张图不存在“医院不在节点枚举名单里就被拒绝”的具体限制；但通用机制支持此限制，不适合直接作为本场景医院名单维护方式。

当前普通参数节点的输出形态为：

```json
{
  "data": {
    "parameters": {
      "hospital_name": "核心流程模拟医院",
      "start": "2025-08-01 00:00:00",
      "end": "2025-08-31 23:59:59"
    }
  }
}
```

这里 data 是输出口键，内层 parameters 是该口的内容。示例是合成值，不表示刚收到一条监管请求。缺参时当前默认值逻辑会补值，因此当前输出也未必等于原始请求内容。

## 职责分工（Q13—Q15 均已确认）

```text
监管端选择医院、起止日期、规则
  → 公共任务 API：按统一接口约定受理、定位流程、绑定版本、保存输入
  → 返回任务编号和受理状态
  → Worker 启动绑定版本
  → 画布“任务入参”：提供本次已受理的条件与任务上下文
  → Database 等节点引用医院与时间执行查询
```

### 字段定义与具体值分别展示

- 双方接口约定仍须定义字段名称、含义和类型，否则建图时无法知道下游能选择哪些参数。这些定义由平台统一提供，建议不让用户在每张监管流程画布里重复录入。
- 编辑画布且尚未关联任务时，展示字段和来源，值显示“尚未接收”；不能展示一个假装已经收到的医院或日期。
- 查看某次任务时，展示该任务的实际入参及任务编号。并发任务不能互相覆盖，更不能以“最近一次请求”冒充当前所看任务。
- 模拟调试通过单独的测试请求提供样例，明确标识为模拟任务；建议不再依赖入口节点 default 静默补入样例。
- 节点输出建议包含医院、开始时间、结束时间及本次规则选择。规则在公共入口已确定执行流程，进入节点后不重新选流程；所绑定版本属于平台任务上下文。具体对象层级和接口字段名待决定确认后对齐，不在本轮凭空定义正式接口。
- 下游引用任务参数，不将单份任务上下文混为数据库明细。隐藏编辑器同时必须保留契约提供、发布编译、参数下拉和运行时注入，单改 UI 不能实现以上行为。
- 子流程 dataset_fields 和其他通用参数节点用途不在本轮改造决定范围内。

### 输入检查边界

用户关于不应在节点中固定医院 Enum、静默补默认医院或日期的质疑符合本场景需求。但“不由节点用户设置校验”与“系统完全不确认请求能否执行”是两件事。

Q14 已确认：公共 API 保留最小结构和可执行性检查，约定字段缺失、医院名为空、日期无法解释、起始晚于结束、规则无对应可执行流程等问题明确返回；不重新判定监管选择的业务理由，不维护节点内固定医院名单。日期具体表示继续遵循双方明确的接口约定，不能猜测或悄悄改变查询期间。监管入口现已实现这一行为，其他通用流程仍保留原校验机制。

现有调用方鉴权、方案来源授权、任务版本绑定和重复提交处理不因隐藏节点 Required/Enum 而被撤销。这些是任务服务已有职责；本轮不扩展成异常分支开发。

Enum 是合法的通用固定取值约束，但不代表本业务应在画布固定医院或时间。规则能够路由到流程来自双方明确的规则与流程关系，不应被描述为禁止监管选择其他医院的枚举设置。

### 监管任务编号

Q15 已确认：接收、保存并展示监管编号与平台 task_id 的对应关系。监管编号不参与医院或时间筛选。本地实现使用 external_task_id，与 Idempotency-Key 分开保存、处理；正式对接字段名仍需双方对齐。

## Q13 追问：只读展示是否足以成为入口

用户最初暂不决定 Q13，要求先说明入口本应如何设计、是否满足业务和时序交互；随后已同意推荐方案并授权实施。下面保留当时的职责说明。

结论：只增加只读展示框不够。建议的完整能力是“任务入口”：运行时为流程提供本次已受理任务的参数与上下文，编辑或查看界面以只读方式呈现。只读是界面编辑权限，不代表节点只显示文字、没有运行时输出。

### 三个层次

| 层次 | 职责 | 不应混淆的概念 |
|---|---|---|
| 系统受理入口 | HTTP 受理、最小检查、规则路由、绑定发布版本、保存任务与监管编号、返回受理凭据 | 不能用一个画布展示组件替代任务 API |
| 流程执行入口 | Worker 启动后，获得该 task_id 对应的已保存条件，向下游提供任务参数和上下文 | 节点不重新发起受理、选择流程或等待人工点击确认 |
| 节点查看界面 | 未关联任务时显示字段约定；关联任务后显示该任务实际值与编号 | 页面打开、选择任务或点击节点不应成为运行前提 |

本次采用显示名称 Business Task Start（任务开始），新增组件而不重命名已有 BusinessParameters 类。任务入参是该节点提供的内容，而不应被解释为整个任务服务的全部能力。

### 对照时序图

| 时序动作 | 应负责的部分 |
|---|---|
| 监管提交医院、结算时间、规则与监管编号 | 公共任务 API |
| 解析规则、绑定发布版本、保存条件和待执行记录 | API 与任务存储；保存后再返回受理状态 |
| 返回 task_id 与受理状态 | API；此时是受理成功，不宣称业务已执行完成 |
| Worker 领取待执行任务、HTTP 启动绑定版本 | Worker 与平台执行服务 |
| 流程获得本次医院、时间、规则及编号 | 任务入口运行时输出；按任务隔离，不读全局最后一次请求 |
| 查询结算、关联检查和序列、调用影像 API、比较结果 | 已绑定版本的各业务节点 |
| 保存实际清单、证据、结果并汇总 | 执行服务与结果存储；满足完成条件后才标记完成 |
| 监管查询状态与已保存结果 | 公共任务查询 API；不通过入口节点回传最终结果 |

此分工能覆盖时序图的正常核心交互，但其成立前提是各部分真实接通，不能用“只读页面已显示参数”作为整条链路验收依据。固定入口契约、完整上下文输出、监管编号接入及任务关联预览现已实施，并通过独立小图连接公共 API、Worker 和结果查询进行验证。数据库替代检查/序列 API 的整图仍未验收。

### 任务入口正常路径验收依据

1. 测试请求经公共 API 受理，返回平台任务编号，能找到对应监管编号和原始业务条件。
2. 未打开画布页面时任务仍能自动启动；无须在节点中手填医院、时间或点确认。
3. 流程执行所用的医院、时间、规则与所查任务一致，下游参数选择在建图时可用。
4. 两个不同医院或期间的任务各自使用本任务条件，查看任务时不互相覆盖。
5. 结果保存并达到完成条件后，监管查询接口返回对应任务状态与结果。

## Q13—Q15 实现记录

### 入口与兼容

- 新增 `Business Task Start`，内部 kind 为 `taskinput`。现有 `BusinessParameters` 类名和通用子流程能力保留。
- 新入口配置固定为空对象，禁止在画布里加入 parameters、default 或 enum。字段定义由公共 catalog 自动提供，发布包记录 `regulatory.v1`。
- 同一监管流程只能有一个 Task Start，不与通用 Parameters 混用；监管入口不能作为子流程重新接收一次任务。
- 固定入参沿用 `hospital_name/start/end`，维持现有数据库绑定。规则由顶层 `scheme` 选择，监管编号使用顶层 `external_task_id`。
- 任务上下文另外提供 scheme、rule_name、external_task_id、task_id、release_id、version，均可在下游任务参数选项中引用。规则名称在受理时保存，修改方案名称不会改变历史任务的入口输出。
- 入口输出形态为 `{ "parameters": {医院与起止时间}, "task": {规则、编号与版本} }`。它是任务上下文，不冒充数据库明细数据集。

### 对接请求

```json
{
  "scheme": "发布并启用的方案编码",
  "external_task_id": "MOCK-REG-001",
  "parameters": {
    "hospital_name": "核心流程模拟医院",
    "start": "2025-08-01 00:00:00",
    "end": "2025-08-31 23:59:59"
  }
}
```

提交到 `POST /api/v1/business/tasks`，沿用调用来源凭据和 `Idempotency-Key` 请求头。监管编号是业务关联编号；幂等键是本次提交的去重标记，未将两者强制设为相同。监管界面显示名称与 scheme 编码需按方案列表对应，不自动猜测中文规则名。

医院和日期必须显式传入；日期按北京时间解释，使用 `YYYY-MM-DD HH:mm:ss`，检查真实日期及开始不晚于结束。保持原始字符串，不改医院名、不扩大查询期间、不补默认值。字段缺失或无法执行的输入返回 422；未知或无权访问方案继续遵循原入口的 404，未激活版本继续返回 422。

检查仅在监管任务受理时执行。Worker 运行时读取已保存输入，不再次按节点配置校验。历史通用任务仍使用原参数机制。

### 保存和界面

- 使用附加表 `business_task_input` 保存监管编号和受理时规则名称，关联既有任务；不改写历史任务表和历史参数。
- 未选任务时显示字段与“尚未接收”；选定任务后显示其实际值。按画布筛选任务并支持翻页；任务或画布切换后不展示旧响应。
- 任务详情页展示相同输入凭据。普通画布编辑不改变原始任务输入。
- 方案页对监管方案提供独立“提交测试请求”操作，显式填写监管编号及三个参数；测试值不会保存为节点默认值。
- 新建方案可选择“监管任务”模板，也可以从 Business 分类拖入 Business Task Start。

3. 在“方案”页面找到 `acceptance.taskstart.5ac08f2620`，用“提交测试请求”另行输入监管编号、医院和起止时间。该操作创建新任务，不改画布的输入定义。任务结果可在“任务与结果”查看。

可重复执行的验收命令（项目根目录，服务启动后）：

```bash
UV_CACHE_DIR=/tmp/langflow-uv-cache uv run --no-project \
  --python deploy/verification/.cache/runtime/bin/python \
  python scripts/business/verify_task_start.py --migrate-core --verify --browser
```

重复执行会创建新的小型验收方案，实际编号以生成的 acceptance.json 为准。凭据从本地私有 `.env` 读取，不写入验收记录。核心画布迁移前备份保存在 `deploy/verification/.cache/core-before-task-start.json`。
